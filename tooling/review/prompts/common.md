## 守ること

- 「見る範囲」に入るものだけを指摘する。範囲の外で気づいたことは、どれほど大事に見えても書かない。ほかの観点は、別のレビューが見る。
- 見るのは、差分が足したり変えたりしたものと、その影響だけ。差分と関係の無い、元からある問題は書かない。
- 「割り切ったこと」の節にある件は、前提が変わっていなければ、指摘し直さない。前提が変わった(実害が出るようになった)と考えるなら、どの前提がどう変わったかを書いて指摘する。
- 直下の `AGENTS.md` の「まだ決めていないこと」は、ユーザーと話して決める。直し方の案で、それを決めない。
- 高・中の指摘を出す前に、レビュー担当自身が、誰がどんな手順で変更箇所に到達するかをたどる。仕様や画面の案内から期待できる結果と、差分を適用したときの実際の結果を比べ、誰にどんな実害があるかを確かめる。
- 起こりやすさは、その操作をする人にとっての条件で判断する。たとえば、キーボードを使う人が保存のたびに困るなら、そう書く。テストで何度でも再現できることと、実際の利用者がその条件に出会う頻度は別に確かめる。頻度の実測が無ければ、通常の手順のどこで条件がそろうかを示し、確率を推測で数値にしない。セキュリティの観点では、実際に公開されている入口と必要な権限から到達可能性を判断する。
- 指摘するのは、今のコード・テスト・story・文書の手順の中か、人やエージェントが普通に行う開発や操作の中で起きるものだけ。起こすために、人もエージェントも普通は書かない定義・値・書き方を新しく置く必要があるもの(空白で区切った9語を variant の名前にする、hook を `satisfies` で包む、など)は、指摘にしない。lint のルールの見逃しや誤った診断も、人やエージェントが普通に書く形に限る。
- 好みの違いだけの書き換えは、指摘にしない。
- ファイルを書き換えない。読むだけにする。

## 重要度

| 重要度   | 付けるもの                                                                                                       |
| -------- | ---------------------------------------------------------------------------------------------------------------- |
| 高       | merge すると実害が出る。データが壊れる・失われる、権限の無い人が読み書きできる、動かない、など。                 |
| 中       | 普通の開発や操作で実害が出る。文書や規約の違反なら、どの判断を誤らせるか、どの約束が守れなくなるかを示せる。     |
| 低       | 直すとよくなるが、merge を止めるほどではない。                                                                   |
| 実害無し | 実害が無く、直すのに骨が折れる(細工した入力でだけ起き、500 とログで済む失敗など)。「割り切ったこと」に書く候補。 |

高と中が1件も無ければ LGTM とする。低と実害無しが残っていても LGTM。

## 出力の形

Markdown で、次の形だけを出す。前置きや、作業の経過は書かない。

```text
## 指摘

### 1. [中] 一行の要約

- 場所:`path/to/file.ts:42`
- 経路:誰が、どんな前提で、何をすると起きるか。高・中なら、その人が通常の使い方でこの条件に出会う場面も書く。
- 起きること:期待する結果と実際の結果。高・中なら、その違いで誰がどう困るかも書く。
- 根拠:期待する結果の根拠と、差分が実際の結果をもたらすと確かめたコード・テスト・文書。
- 直し方の案:どう直すか。

## まとめ

高 0件・中 1件・低 0件・実害無し 0件。

VERDICT: CHANGES_REQUESTED
```

- 経路を書けない指摘は、出さない。高・中の根拠が足りない場合は、その重要度で報告しない。
- 指摘は、重要度の高い順に並べ、番号を振る。指摘が無ければ、「## 指摘」の下に「無し。」とだけ書く。
- 最後の行は、高と中が0件なら `VERDICT: LGTM`、1件でもあれば `VERDICT: CHANGES_REQUESTED` にする。この行の後ろには何も書かない。
