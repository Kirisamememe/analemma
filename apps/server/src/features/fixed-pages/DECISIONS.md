# 決めたことと理由(fixed-pages の feature)

固定ページ(About・Colophon など)を扱う。フェーズ1は固定ページだけを作る(ユーザーと決めた。開発の基盤の効果を、一番シンプルなもので確かめるため)。

## 列と JSONB

- 固定ページは、メタデータ(slug・タイトル・種類・公開状態・並び順・日時)を列に、中身を JSONB に持つ(ユーザーと決めた)。中身の形は種類ごとに決まっていて、保存のときに必ず種類の定義で検査する。自由な JSON は持たない。
- 種類は、ページを作るときに選び、後から変えない。変えると、中身を別の定義で検査し直すことになり、どちらの定義のデータを残すかを決める必要が出る。
- slug は、種類ごとではなく、固定ページの全体で1つにする。公開サイトの URL に使いやすいように。
- ID は PostgreSQL 18 の `uuidv7()` で作る。
- 公開 API は、種類と slug で引き、種類が違えば無いものとして返す。公開サイトは、ページの種類を知ったうえで引き、その種類の定義から推論した型で中身を受け取るので、違う種類のページを返すと、型と中身が食い違う。

## 保存と検査

- 中身の検査は、kinds の feature の `checkContent`(contract の `toContentSchema`)で行う。定義に無いキーは、検査で落とさずに残す。項目を消した定義を受け取っても、データを JSONB に残し、古いサイトに戻したときにデプロイを止めないため(ユーザーと決めた)。
- 管理用 API の `get` は、定義に無いキーも含めた中身を返す。管理画面は、フォームに出さないキーも、そのまま送り返す(管理画面の土台を作るときに守る)。送り返さないと、書き換えたときに消える。
- 公開 API は、今の定義にある項目だけの中身を返す。公開サイトが推論する型と同じ形にする。
- 中身を書くのは、`editing/save-fixed-page.query.ts` の `saveFixedPage` だけにする(作成と書き換えの両方)。編集履歴を足すときは、ここで同じトランザクションに写しを書く(ユーザーと決めた。編集履歴そのものは後で足す)。
- 中身が定義に合わないときは、`INVALID_CONTENT` に、合わない場所(キーと添え字の並び)と zod の issue の code を、20件まで添える。管理画面が、フォームのどこに出すかを決められるように。
- 保存のときは、種類の行の共有ロック(`FOR SHARE`)を取ってから、定義を読んで検査する。定義を受け取る側は、種類の行に `FOR NO KEY UPDATE` を取ってから、既存のページを検査する。2つが重なっても、検査に使った定義と違う定義のもとで、ページが保存されることは無い。
- 書き換えでは、固定ページの行のロックを取ってから、種類の行のロックを取る。定義を受け取る側はページの行のロックを取らないので、順が食い違っても、互いに待ち合わない。

## 公開状態

- 新しいページは、公開していない状態で作る。データが入って公開するまで、公開 API からは見えない(ユーザーと決めた)。見つからないものと公開していないものは区別しない。
- 公開状態は `publishedAt` の有無で持つ。公開状態の判定は、`published/match-published.query.ts` の `isPublished`(行を見る)と `matchPublished`(SQL の条件)だけで行う。
- 公開し直しても `publishedAt` は変えず、非公開に戻すと消す。公開した日時は公開サイトに出しうる値で、公開を押し直すたびに変わると困る。
- `updatedAt` は、タイトル・slug・中身を変えたときだけ進め、公開と並び順の変更では進めない。公開サイトに「最終更新」として出せるように。

## 並び順

- 並び順は、種類ごとではなく、すべての固定ページを1つの列で並べる。新しいページは最後に付く。
- 並べ直しでは、すべてのページの ID を、並べたい順に送らせる。今あるページと1つでも食い違えば、`ORDER_MISMATCH` で断る。管理画面が古い一覧のまま並べ直して、ほかで作ったページの位置を黙って決めてしまわないように。確かめる前に、すべての行のロックを ID の順に取る。
- 並び順の値が重なったときは(「割り切ったこと」)、作った日時と ID の順に並べる。

## まだ作っていないもの

- 削除は、仮に物理削除にしている(server の「まだ決めていないこと」。ユーザーと決める)。
- ビジネスイベント(キャッシュの無効化など)は、dispatcher を作るときに足す。今は、書き込んだ後に何も配らない。
- canonical URL は、公開サイトが固定ページをどのパスに置くかが決まってから、mapper で作る。今は slug だけを返す。

## 割り切ったこと

- **書き換えの slug の競合**:書き換えで slug を変えるときは、ほかのページに使われていないかを確かめてから書く。同時に2つのページを同じ slug に書き換えると、後の方が一意の制約で失敗し、500 とログになる。管理者は1人で、ミリ秒の差で同じ slug を2つのページに付けることはまず無い。作成の競合は `ON CONFLICT DO NOTHING` で `SLUG_TAKEN` にしている。
- **並び順の値の重なり**:新しいページの並び順は、今の最大の値に1を足して決める。同時に2つ作ると同じ値になるが、作った日時と ID の順に並ぶだけで、並べ直せば直る。
- **並べ直しと作成の重なり**:並べ直しがロックを取った後に作られたページは、並べ直しの確かめから漏れ、最後に付いたまま残る。並べ直しは成功し、そのページの位置が変わらないだけ。
