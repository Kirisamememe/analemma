## 見る範囲

変更したコードが、決めた仕様のとおりに振る舞うか。仕様は、テスト・contract・`DECISIONS.md` に書いてある。

- 境界値、空・1件・上限、重複、並び順、同時の書き込みで、仕様と違う結果にならないか。
- 途中で失敗したときに、書きかけの状態が残らないか(トランザクションの範囲、後片付け)。
- 想定内の失敗(`_tag` 付きの判別共用体で返す失敗)と想定外の失敗(throw する失敗)の分け方が、呼ぶ側の扱いと合っているか。
- DB の形と API の形をつなぐ mapper、migration と既にある行の扱い、公開状態の判定が、仕様と合っているか。
- 件数が増えると実害が出る無駄(1件ずつの問い合わせなど)が無いか。
- 管理画面の state を足すか、置く場所を変えた変更で、`DECISIONS.md` の「再レンダリングの期待」とそのテストを見直しているか。期待が、その画面で一番頻繁に変わる state と、件数に比例して増える部品を挙げているか。テストが、もともと再レンダリングしない範囲だけを確かめて、小さな子孫の操作が祖先や兄弟を巻き込む変更を通していないか。
- テストが仕様を確かめているか。実装をなぞるだけで、仕様を壊しても通るテストになっていないか。変えた振る舞いにテストがあるか。

## 見ない範囲

- 悪用につながる穴(認証・認可・入口の守り・入力の境界・秘密の扱い。セキュリティの観点)。入力の検証や上限が仕様と違うだけで、悪用につながらないものは、この観点で見る。
- 管理画面の見た目・操作・アクセシビリティ(UI/UX とアクセシビリティの観点)。
- 書き方・フォルダ・`DECISIONS.md` に書いたかなどの、リポジトリの約束(規約やルールの遵守の観点)。
- 文書・コメント・テストの名前・管理画面の文言の言葉(言葉の観点)。文書がコードと食い違っているときは、コードの方が仕様と違うときだけを書く。
