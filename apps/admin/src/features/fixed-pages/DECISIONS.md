# 決めたことと理由(管理画面の固定ページ)

## 一覧と並べ直し

- 画面は `/fixed-pages`(固定ページ)。並び順のまま、タイトル・公開状態・slug・種類のラベル・更新日時を出し、公開と非公開の切り替え・並べ直しを置く。削除は行に置かず、編集の画面にだけ置く(「編集の画面」)。見出しと、ページが無いときの欄に作成(`/fixed-pages/new`)への導線を、行に編集(`/fixed-pages/$id`)への導線を置く。
- 種類のラベルは、種類の一覧(`admin.kinds.list`)から引く。種類の一覧を読めないときや、一覧に無い種類のページでは、種類の名前を出す。種類は一覧の補足で、読めなくても固定ページの操作はできるので、一覧全体を失敗にしない。種類の一覧が届くまでは、一覧を出さずに読み込み中にする。先に名前で出すと、普段は名前がすぐラベルに替わってちらつく。
- 一覧と種類の一覧の両方を読み込めなかったときは、一覧の「もう一度試す」で両方を取り直す。どちらかの応答を待っている間は、「もう一度試す」を押せないようにする。固定ページを取れても、種類の一覧を取り直している間は、一覧を出さずに読み込み中にする(上の「種類のラベル」と同じく、名前からラベルに替わってちらつかないように)。種類の一覧だけを読めないときは、種類のラベルの代わりに種類の名前を出すので、欄は出さない。
- 種類の一覧と一度開いた種類の定義は、固定ページのタブ内で15分使い回す(ユーザーが決めた)。一覧・作成・編集を行き来するたびに同じ選択肢や項目を待たずに済む。15分を過ぎて開くと前の値で描き、裏で取り直す。一時的な失敗で種類や入力中のフォームを消さない。初回の失敗では従来どおりやり直せる。タブを離れたときと、ログアウトやセッション切れのときは捨てる。固定ページの一覧や本文は毎回取り直す。空の種類一覧も15分使う。種類が見つからなかった場合は、開き直すたびに取り直す。
- 裏で取り直した定義で項目が変わったとき、未編集なら新しい項目を表示する。入力中は元の項目と値を保ち、入力を控えてから読み込み直すように案内する。新しい定義で入力を初期化すると、削除された項目や確定する前の値を失うため。
- 公開と非公開の切り替えは、戻せる操作なので、確認の Dialog を出さずにその場で送る。成功を Toast で知らせ、一覧を取り直す。ほかで消えたページの操作は `NOT_FOUND` になるので、一覧を取り直したことと一緒に Toast で知らせる。想定外の失敗でも一覧を取り直す。変えられてから応答だけが失敗したときに、一覧を server に合わせるため。
- 「公開する」は塗りのボタン(`primary`)、「非公開にする」は枠のボタン(`secondary`)にする。役割が違うので、幅だけでなく見た目でも分ける(ユーザーが決めた)。
- 並べ直しは、置いたらすぐに送り、保存のボタンを置かない。全部の ID を並べた順に送る。送っている間は、置いた順に並べ、並べ直しを止め、一覧の上に保存していることを出す(行の中の操作は使える)。答えが届いたら一覧を取り直し、結果を Toast で知らせる。`ORDER_MISMATCH`(ほかで固定ページが増えたか減った)なら、取り直した一覧を出し、並べ直し直すよう知らせる。想定外の失敗なら、元の並びに戻して取り直す。

## 編集の画面

- 一覧へ戻るリンクは、作成と編集の route ごとに1つの枠に置き、読み込みの前後では枠の中だけを切り替える。読み込む間にリンクへ移した focus が、フォームを出したときに外れないようにするため。
- 見出しの操作に、削除と保存を並べ、フォームの下にも保存を置く(長いフォームで、保存が一番下にしか無かった。ユーザーが決めた)。見出しをフォームの中に置き、上の保存も送信のボタンにする。作成の画面には削除を置かない。
- 編集の画面は、固定ページと種類の定義を読み終えるまで、同じ読み込み中の欄を出し続け、見出しの補足(種類)も出さない。前は、固定ページを読んだところで欄を作り直していたので、骨組みが一度消えてから出直し、補足が種類の名前(colophon)から、種類の定義を読んだ後のラベル(Colophon)に替わってちらついた(ユーザーが見つけた)。種類の定義は、固定ページを読んで名前が分かるまで取得しない。
- 削除のボタンは、ゴミ箱のアイコンだけにする(名前は「固定ページを削除」)。赤い「削除」のボタンは、タイトルを出した確認の Dialog の中にだけ置く(ユーザーが決めた)。削除は物理削除で戻せないので確かめる。種類の定義を読み込めなくても、固定ページを取得できていれば、タイトルを確かめて ID で削除できる。
- 種類の定義を読み込めなかった編集の画面と、種類を選んだ後の作成の画面は、何を読み込めなかったか(種類の定義)と、中身の項目が種類の定義から作られることを、読み込めなかった欄で伝え、取り直せるようにする。編集の画面では固定ページは取得できているので、見出しの削除のボタンは残し、タイトルを確かめて削除できる。種類の定義を取り直している間は、削除のボタンを押せなくする。取れると編集のフォームに替わり、削除の Dialog ごと消えて、削除の結果を出せなくなるため。固定ページそのものを読み込めなかったときも、同じ欄で取り直す。
- 削除できたら、Toast で知らせて一覧に戻る。一覧は画面を離れたときに捨てているので、戻ってから読み込む(`apps/admin/DECISIONS.md` の「server の API の呼び方」)。応答が届いたときに編集の画面を閉じていたら、一覧へは移らない。移ると、移った先の画面で離れる前の確かめを飛ばし、そこで入力した値を消す。ほかで消えていたら(`NOT_FOUND`)、Dialog を開いたまま失敗の Toast で知らせ、削除のボタンを止める。想定外の失敗も失敗の Toast で知らせ、送り直せるように Dialog を開いたままにする(`apps/admin/DECISIONS.md` の「知らせの出し分け」)。前の送信の結果は、Dialog を開くときに消す。削除の確認のボタンは、Dialog を閉じ始めた後の押下では送らない(タッチの長押しの遅れた click。`src/ui/DECISIONS.md` の「割り切ったこと」)。パスキーの削除と違い、再認証の OS の画面で止められないため。
- 保存していない変更があるまま画面を離れるときは確かめる(ユーザーが決めた)。管理画面の中の移動は Dialog で確かめ、タブを閉じる・読み込み直すときはブラウザに確かめさせる。変更があるかは、開いたときの値(保存できたら、送った値)と今の値から、保存で送る slug・タイトル・中身を作って比べる。入力して元に戻した値や、送らない未入力の違いでは確かめない。年・月・日の一部だけを入力した日付と、確定する前の数値はフォームの値に反映されないので、入力欄にこうした変更があるときも確かめる。保存の応答を待つ間は、送った値とも比べる。元の値に戻しても、保存が成功すれば送った値が残るため。保存できた後の移動(作成から編集の画面へ)と、削除した後の移動は確かめない。
- 保存の失敗は、想定外の失敗(通信の失敗など)も、server が断った値(`SLUG_TAKEN`・`INVALID_CONTENT`)も、ページや種類が無いことも、失敗の Toast で知らせる(`apps/admin/DECISIONS.md` の「知らせの出し分け」)。slug が重複したときと、中身の issue が項目に結び付くときは、該当する欄にも誤りを表示する。同じ画面で保存を送り直すときは前の失敗の Toast を閉じ、新しい結果だけが残るようにする。
- 種類を選んで作成の画面を開いたら、slug の欄に focus を移す。押した種類のボタンが消え、focus の行き先が無くなるため。最初の欄は、作るページの slug を決める欄で、Tab で見出しの保存などを通らずに入力を始められる。種類を読み込む間に一覧へ戻るリンクなどへ focus を移していたら、そこに残す。URL や履歴で作成の画面を開いたときは、画面を移ったときの focus(`apps/admin/DECISIONS.md` の「割り切ったこと」)と同じく、移さない。
- 「必須」のラベルは、slug・タイトルと、種類の定義で `optional` でない項目に付く。真偽値の項目は、いつも値を持ち、「チェックが必須」と読めてしまうので付けない。group と repeat の見出しにも付けない。repeat は要素が無くても保存でき、group の中の項目には、それぞれ付く。

## 中身とフォーム

- group と repeat は、見出しの丸から中身へ線を引く。枠で囲むと、入れ子が深くなるほど段ごとに右の余白が重なり、入力欄が狭くなる。丸は 28px、アイコンは 16px で線幅を 1.5px、階層の線と丸の枠は 2px にする(ユーザーが決めた)。丸と名前の間を 4px 空け、名前と中身を同じ列に置く。見出しの下と子の間の余白は、そこを通る線の高さで決める(group は 16px、repeat は 24px)。線は最後の子への枝で止める。最後が値を持つ項目なら、補足と誤りの知らせを含めた項目の下端まで引く。
- 枝の幅は 19px とし、丸の中心を通る線から子の丸の中心の高さにつなぐ。帯に向かう枝は要素名の1行目の中心の高さにつなぎ、名前や操作が折り返しても位置を保つ。子の丸と帯の左端は、親の名前の列に置く。丸と名前の間を 4px にして、各段の横の線を短くした(ユーザーが決めた)。帯をはみ出させずに名前と中身をそろえるため、帯の名前と要素の中身(誤りの文・項目のラベル・入力欄)をともに 12px 内側に置く。追加ボタンは入力欄と同じ枠の部品なので、左端を要素の入力欄にそろえ、その枝だけを 12px 長くする(ユーザーが決めた)。並べ替えと削除のボタンは、どの要素を操作するか分かるように、その帯の右に置く。幅が足りないときは操作を次の行に送り、そこでも3個が収まらなければボタンの間で折り返す。編集欄の幅が 16rem を下回ると、丸は 1.25rem に小さくし、枝と帯や入力欄の左右の余白を詰める。文字を大きくしても、入れ子の値を何文字か続けて読める幅を残す。
- フォームの最上位の段・group・repeat の各要素は、それぞれの段で、項目の値と、定義に無いキーの値を分けて持つ。server は中身を丸ごと置き換えるので、定義に無いキーも元の段に戻して送る。キーと値の組から `Object.fromEntries` でオブジェクトを作り、`__proto__` もその名前のキーとして扱う。
- text・longText・url の未入力は空の文字列、number・date・select の未入力は `null` にする。これで `0` も入力した値として扱える。boolean はいつも値を持ち、新しい固定ページでは項目の既定値から始める。
- 保存した中身の値は、contract のスキーマと select の選択肢で確かめる。boolean は保存済みの真偽値をそのまま表示し、値が無いか真偽値以外なら項目の既定値を表示する。ほかの項目は、値が無いときや定義と食い違うときに未入力に戻す。server は取得した中身をそのまま返し、保存時に値の無い真偽値へ既定値を入れる。公開サイトの client は、ページを読むときに既定値を補う。object でない repeat の要素も位置を保ち、管理者がその場所で直せるようにする。
- 送るときは未入力の項目のキーを省き、必須かどうかの検査は server に任せる。必須の group は空でも送り、内側の項目に issue が付くようにする。必須の repeat は要素が無ければ空の配列を送る。任意の group を送るのは、内側に入力した値・repeat の要素・定義に無いキーのいずれかがあるときだけ。既定値のままの boolean は入力に数えない。内側の必須の group・repeat が空であることだけでは、外側の group を入力したことにはしない。
- repeat の要素にはフォームを作るときに `crypto.randomUUID()` で ID を付ける。要素を動かしても値と ID は一緒に動き、保存には値だけを使う。issue の添え字は送ったときの並びで ID に読み替える。値を持つ項目・group・repeat・repeat の要素までたどれた issue はその場所に結びつけ、結び付かない issue は `unbound` として返す。画面はその場所と誤りの内容を保存失敗の Toast に表示する。
- TanStack Form には、入力値と repeat の ID の並びを別々に持たせる(`editor/logic/flat-content.ts`)。場所には項目のキーと要素の ID を `/` でつないで使う。`ContentForm` は再帰する型なので、そのまま TanStack Form の値にすると、field の名前の型(`DeepKeys`)が無限に展開されて型検査が止まる。添え字ではなく ID を名前に使うので、並べ替えても入力・誤りの知らせ・touched は同じ要素に残る。
- server が断った値(`SLUG_TAKEN` と、結べた `INVALID_CONTENT` の issue)は、`form.Form` の `validationErrors` で欄ごとに出し、その欄の値を変えたら消す。group・repeat・repeat の要素に結べた issue は、そのまとまりの見出しの下に出す。issue の文言は `code` から選び、zod の英語の `message` は出さない。結べない issue は、server が返した場所を添えて、失敗の Toast の文に入れる。保存の応答を受けた直後は次のフレームでも誤りの欄が DOM に反映されていないことがある。誤りを反映した ref callback から、primitives の `focusFirstInvalidField` で、画面の上にある最初の誤りの欄に focus を移す(`src/components/forms/DECISIONS.md` の「送信の検証で止めたときの focus」)。group・repeat・repeat の要素の誤りは、まとまり(`fieldset`)に `data-invalid` を付け、まとまりそのものに focus を移して、見出しと誤りを読ませる。まとまりが focus を受けるのは誤りがあるときだけにし、キーボードで移った先は、そのまとまりの見出しに focus の ring を描いて示す。誤りの無いまとまりの見出しを押しても、まとまりに focus は移らない。上の保存ボタンを押したときも、下の欄の誤りが見える位置まで scroll する。
- 並べ替えで要素が端に着き、押したボタンが無効になったら、同じ要素の反対の向きのボタンに focus を移す(無効のボタンは focus を受け取れない)。削除した後は、次の要素の削除ボタンに、末尾なら追加ボタンに focus を移す。
- 固定ページのフォームは `onSubmit` で保存を送り、応答を待たずに `onSubmit` を終える。応答を待つ間は入力を続けられ、Enter で保存したときも入力欄に focus が残る。保存のボタンと Enter での再送は、保存が終わるまで止める。
- 編集の画面は、開くたびに固定ページを読み直す。種類の定義は同じタブで取得済みならその値でフォームを作る(「一覧と並べ直し」)。更新できたら、固定ページのキャッシュを更新の応答で差し替え、取り直すのは一覧だけにする。保存の後に取り直すと、取り直している間に画面を離れて戻ったときに古い値でフォームを作り、取り直しが失敗するとフォームが消える。

## 割り切ったこと

- **数値の欄の、数になる前の入力**。数値の欄で、保存済みの値(7 など)を `-` に書き換え、focus を残したまま「固定ページの一覧」を押すと、離れる前の確かめが出ずに `-` が消える。履歴から移って確かめが出たときも、「編集を続ける」で欄は 7 に戻る。消えるのは、まだ数になっていない入力だけで、保存済みの値は残るので受け入れる。
- **画面を離れる前の確認中にブラウザの履歴をもう一度移動したとき**。固定ページの入力を変えてブラウザの「戻る」を押し、確認に答える前に「進む」を押して「編集を続ける」を選ぶと、Chrome ではブラウザが再読み込みを確かめる。再読み込みを取り消してもう一度「戻る」を押すと、入力は残るが URL だけが一覧になる。最初の確認に答えてから次の移動をする場合は起きない。確認中の履歴移動まで扱うには TanStack Router が待っている移動とブラウザの履歴を独自に合わせる必要があり、手間に見合わないので受け入れる。

- **削除して一覧に戻った直後の focus**。キーボードで最後の1件の削除を確定すると、focus は文書に戻る。Chrome で広い画面を開いて試すと、Tab は成功の Toast、閉じるボタン、ナビを通り、8回目で一覧の「新しい固定ページ」に着いた。キーボードで操作は続けられるので、今はほかの画面遷移と同じ扱いにする。余裕ができたら、削除後に一覧の操作へ直接 focus を移す。

- **作成の応答とブラウザの「戻る」が重なったとき**。作成を送ってから応答を待つ間にブラウザの「戻る」を押し、画面を離れる前の確かめに答える前に作成が成功すると、履歴の1つ前が編集画面に置き換わり、「進む」側に作成画面が残る。固定ページは保存される。普段は数十ミリ秒の応答待ちに戻ったときにだけ起き、影響は前後の履歴に限られる。防ぐには、ブラウザが履歴を移す処理と、router が移動を止める処理を待ち合わせてから編集画面へ移る仕組みが要るので受け入れる。

- **取り直しの失敗と重なり**:一覧の取り直しは、失敗しても呼び出し元に返さない(`invalidateQueries` の既定)。`ORDER_MISMATCH` や `NOT_FOUND` の後の取り直しが失敗すると、一覧は読み込めない知らせに替わるのに、「一覧を読み込み直しました」と知らせる。また、並べ直しの後の取り直しの最中に、ほかの行の公開を切り替えると、先の取り直しが中断されて保存中の表示が消え、後の取り直しが届くまでの間(普段は数十ミリ秒)、保存する前の並びが出て、並べ直しを始められる。どちらも、書き込みと取り直しの両方が失敗するか、数十ミリ秒の間に操作を重ねたときだけ起き、次の取り直しで正しい一覧に戻る。取り直しの結果を書き込みの結果と別に扱う作りは、server の状態の包み(`src/api/server-state/`)ごと直す必要があり、手間に見合わないので受け入れる。
- **画面をまたいで残る保存の失敗の Toast**:保存の失敗の Toast を閉じずに画面を離れ、同じ固定ページを開き直して保存に成功しても、前の失敗の Toast は残る(閉じるまで残る `danger` の Toast)。同じ画面で送り直すときは閉じるが、閉じる関数は編集の画面と一緒に無くなる。残る Toast は前の失敗を正しく伝えていて、閉じるボタンで消せ、送り直しても害は無い。画面をまたいで閉じるには、固定ページごとに閉じる関数を持ち続ける仕組みが要り、手間に見合わないので受け入れる。
- **ログアウトとセッション切れのときの、離れる前の確かめ**:保存していない変更があるとき、ログアウトの後と、セッションが切れて(`UNAUTHORIZED`)ログインの画面へ移るときにも、離れる前の確かめが出る。セッションが切れたときは、入力を写し取ってから離れられる。「編集を続ける」を選ぶと、保存できない編集の画面に残り、次の操作で同じ確かめが出るので、「変更を破棄」で抜ける。ログアウトを送る前に確かめるには、ナビのログアウトと編集の画面の状態をつなぐ仕組みが要り、手間に見合わないので受け入れる。
- **保存を送っている間に離れたとき**:離れる前の確かめで変更を破棄しても、送った保存は取り消さない。届けば保存され、失敗すれば移った先の画面に失敗の Toast が出る。送信を中断するには、取得と保存の全体で進行中の要求を中断する仕組みが要り、起きるのは応答を待つ数十ミリ秒の間に離れたときだけなので受け入れる。
- 任意の group・repeat を空のまま保存してあった固定ページは、保存し直すとそのキーが消える。フォームではどちらも未入力として扱うので、空で保存されていたかを別に持つ理由が無い。
- 任意の group の中身が、既定値のままの boolean だけで保存されていた場合、保存し直すと group ごと省かれる。フォームは、既定値のままの場合と、管理者が既定値と同じ値を選んだ場合を区別しない。
- 保存した中身に無い項目も、フォームを作るときは値のスキーマで検査する(`safeParse(undefined)`)。repeat が1万要素あり、各要素に任意の項目が100個ある中身では、フォームを作る時間が約100ms 伸びる(Bun で計測)。個人サイトの固定ページの repeat はそこまで増えず、フォームを作るのは開くときの1回だけなので、受け入れる。
- 保存を送ってから応答が届くまでの間(普段は数十ミリ秒)に変えた入力は、次のように扱いが崩れる。どれも、その間に入力したときだけ起き、保存し直せば直るので受け入れる。
  - 作成できて編集の画面に移ると、その間の入力は消える。
  - 応答の誤りは送ったときの場所に付けるので、その間に直した欄に古い値の誤りが出る。その間に消した repeat の要素にだけ誤りがあると、保存できなかったことが出ない。
- 保存の応答が届く前に同じページを開き直すと、更新の前の値でフォームを作りうる。応答を待つ数十ミリ秒の間に開き直したときだけ起き、そのまま保存すると古い値に戻すが、管理者が自分で直前に書いた値なので気づける。直すには、保存と取得を待ち合わせる仕組みが要るので受け入れる。
- 保存の応答が届いたときに編集の画面を閉じていたら、固定ページのキャッシュを差し替えない。使う画面の無いデータは持たないので、差し替えても捨てるだけになる。
- 年 `0000` の2月29日を中身に持つ固定ページは、編集の画面を描けずにエラーになる。日付の欄は年 `0000` を扱わない(`src/components/forms/DECISIONS.md` の「割り切ったこと」)。管理画面からは入らず、API へ直に送ったときだけ起きるので、日付の欄で年 `0000` を扱うと決めるまで受け入れる。
- 編集画面を開いたまま真偽値の項目の既定値をデプロイで変えると、まだ値の無いページでも、保存したときに画面に出ている変更前の値が書き込まれる。新しい既定値で編集し直すときは、固定ページ以外のタブを開いて保存済みの定義を捨て、編集画面を開き直す。開いた後の定義まで追うには、グループや繰り返しの中も含め、各項目が保存済みか、管理者が編集したかを別に持つ必要がある。個人サイトで定義の変更とページの編集が重なるときに限られ、保存後も Checkbox で直せるため、画面に出ている値を保存する。
