# 決めたことと理由(auth の feature)

管理画面の認証(パスキーとセッション)の判断。

## WebAuthn の検証(`webauthn/`)

仕様(W3C WebAuthn Level 3)の検証の手順を、ライブラリを使わずに自分で持つ。Better Auth などの認証のライブラリは使わない(リポジトリの `DECISIONS.md`)。手順は純粋な関数で、Web 標準(WebCrypto・`TextDecoder`・`DataView`・`Uint8Array` の base64 の変換)だけで書き、DB も Bun の API も使わない。

- 応答が手順に合わないことは、想定内の失敗として `_tag: "Rejected"` と理由(`problem`)で返す。throw して呼ぶ側で受け止める形にすると、どの失敗が想定内かが型に出ない。理由の文はログに書くためのもので、API の出力には出さない。
- 標準の関数が throw する失敗は、try/catch や `.catch()` で受け止めて、`Rejected` に変えることはしない(try/catch を書けるのは、入口と dispatcher だけ。ユーザーが決めた)。`TextDecoder` は `fatal` にせず、UTF-8 でないバイトを置換文字(U+FFFD)にする。仕様の「UTF-8 decode」も置き換える方で、置き換えた値は、後の照合(origin・`fmt` など)でいつもどおり拒まれる。`JSON.parse` と、WebCrypto の鍵の読み込みの失敗は throw のままにする(「割り切ったこと」)。

### CBOR

- 受け付ける形を、要るものだけに絞る。不定長・タグ・浮動小数・2^53 以上の整数・16段を超える入れ子・重なった map のキーは拒む。受け付ける形が少ないほど、壊れた入力や悪意のある入力で困る所が減る。文字列の UTF-8 でないバイトは、置換文字にして読む。
- map は `Map` で持つ。COSE の鍵は負のキー(`-1` など)を使うので、オブジェクトのキーにすると区別できない。
- 配列と map は、宣言した個数を先に確保せず、1つずつ読む。残りのバイト数より大きな個数を宣言していても、読み進めるうちに「途中で切れている」で拒まれる。
- 値の後ろの余りは、呼ぶ側が決める。authenticatorData では COSE の鍵の後ろに拡張が続く。

### COSE の鍵

- 扱うのは EC2 の P-256(ES256)・OKP の Ed25519(EdDSA)・RSA(RS256)だけ。鍵の型(kty)と曲線(crv)がアルゴリズムに合わなければ拒む。登録の options には、Ed25519・ES256・RS256 の順に並べる。
- WebCrypto は COSE を読めないので、JWK に直して読み込む。曲線の上に無い点などは、WebCrypto が読み込みを断り、throw する(「割り切ったこと」)。
- ES256 の認証器は署名を DER(`SEQUENCE { r INTEGER, s INTEGER }`)で返すが、WebCrypto の ECDSA は r‖s(32 バイトずつ)を受け付けるので、直してから検証する。
- 秘密鍵の項目(EC2・OKP の `d`、RSA の `d`・`p`・`q` など)が混ざった COSE_Key は拒む。届いた COSE_Key をそのまま保存するので、仕様に合わない認証器が秘密鍵を送ってくると、DB に残ってしまう(Codex の2回目のレビューで見つかった)。
- RSA の法は 2048〜4096 ビット、公開指数は 3 以上・奇数・33 ビット以下に絞る。認証器は公開指数 65537・法 2048 ビットを使う。絞らないと、262,144 ビットの法や、1・偶数・法と同じ長さの公開指数でも登録が通り、そうした鍵でのログインを防ぐのを「WebCrypto が false を返すこと」に頼ることになる。巨大な法は、ログインのたびの検証も重くする。法は、バイト数でなくビット数で数える。256 バイトでも、先頭のバイトが小さければ 2048 ビットに足りない。

### authenticatorData と clientDataJSON

- authenticatorData の拡張(ED)は読み飛ばす。末尾に余りがあれば拒む。ログインの authenticatorData に資格情報(AT)が入っていれば拒む(仕様の 6.1 では、ログインの AT は 0)。
- rpIdHash は SHA-256(RP ID) と照らし合わせる。ほかのサイト用の鍵で作られた応答を拒む。
- UP(利用者がその場にいた)と UV(生体認証か PIN で本人を確かめた)を必ず求める。パスキーが管理者のただ1つの鍵なので。BE が 0 なのに BS が 1 の応答は、ありえないので拒む。
- clientDataJSON は、ブラウザが書くので、ページの JavaScript からは書き換えられない。仕様(7.1 の手順5・7.2 の手順8)の UTF-8 の読み取りに合わせ、先頭の BOM を落とし、UTF-8 でないバイトを置換文字にしてから JSON として読む。署名の対象には、届いたバイト列をそのまま使う。
  - type:ログインの応答を登録に流用させない(逆も)。
  - challenge:以前の応答の使い回し(リプレイ)を防ぐ。
  - origin:見た目だけ似せた別のサイト(フィッシング)で作らせた応答を受け付けない。
  - crossOrigin と topOrigin:ほかのサイトの iframe の中で作らせた応答を受け付けない。仕様(7.1 の手順11・7.2 の手順14)は、topOrigin があれば、iframe の中での利用を見込んでいるかを確かめるよう求める。見込まないので、あれば拒む。

### 登録とログイン

- 登録では attestation(端末の機種の証明)を求めず、attestation の署名も検証しない。この公開鍵の持ち主であることは、ログインのたびの署名で確かめる。attestationObject の形(仕様の 7.1 の手順13)だけは確かめ、`fmt` が文字列で `attStmt` が map であること、`fmt` が `none` なら `attStmt` が空であることを求める。`none` のほかの `fmt`(W3C の例の packed など)も、中身を見ずに受け付ける。
- 資格情報の ID は 16〜1023 バイトだけを受け付ける。上限は仕様の手順。下限を置かないと、長さ 0 や 1 の ID でも登録が通る。認証器は 16 バイト以上の ID を作る。空の ID を許すと、空の文字列で引くような誤りに気づけない。
- ログインの署名の対象は `authenticatorData ‖ SHA-256(clientDataJSON)`。clientDataJSON に challenge と origin が入っているので、署名が「この challenge・このサイト」に結びつく。秘密鍵は認証器から出ないので、公開鍵が漏れても署名は作れない。
- `signCount` が、保存した値から戻っても拒まず、戻ったことを返す。複製された認証器の手がかりだが、同期されるパスキーでも起きうる。
- ログインの BE が、登録したときの BE と違っても拒まず、違うことを返し、logger に警告を書く(ユーザーが決めた)。仕様の 7.2 は、バックアップの状態を判断に使うなら、BE が登録したときと同じかを確かめるよう求めるが、ここでは一覧に出すだけで、判断には使わない。BE は鍵を持つ側(認証器やパスワードマネージャー)が立てる値で、攻撃する側は好きに立てられるので、照合しても攻撃は止められない。プロバイダの更新などで本物の認証器の BE が変わると、拒めば管理者を締め出すだけになる。一覧の「同期されているか」は、BE ではなく、ログインのたびに書き直す BS を出す。
- 保存した公開鍵が読めないときと、保存したアルゴリズムと食い違うときは、応答の誤りではなく DB の破損なので、想定外の失敗として投げ、500 とログにする。登録で受け取った鍵の形(kty・crv・長さなど)が合わないときは、受け付けない理由にする。

### テスト

- テスト用の認証器(`webauthn/fake-authenticator/`)は、WebCrypto で ES256・Ed25519・RS256 の鍵を作り、CBOR を組んで署名する。手順を1つずつ破った応答が拒まれることを確かめる。
- テスト用の認証器は自分で書いたものなので、検証の側と同じ思い込みで間違えうる。仕様の作者が作った例として、W3C WebAuthn Level 3 の16章「Test Vectors」(https://www.w3.org/TR/webauthn-3/#sctn-test-vectors)の8例を、16進の文字列のまま `webauthn/w3c-test-vectors.ts` に写した。どの例も RP ID は `example.org`。
  - UV が立っていない例があるので、UV を求めるかは検証の関数に渡す。製品のコードは常に求める。
- テスト用の認証器と W3C の例はテストだけが使うが、`__tests__` にはテストのファイルしか置けないので、別のフォルダとファイルに置く。

### 型付きの lint の不具合への対処

- WebCrypto の型の名前(`JsonWebKey`・`EcKeyImportParams`・`Algorithm` など)は書かず、使う項目だけの形を自分で書く。tsc は Bun の型から読めるが、型付きの lint(tsrs)はこれらを解決できず、error 型として `no-unsafe-*` の診断を出す。TypeScript の検査とルールのぶつかりではなく、tsrs の不具合。tsrs は開発中なので、読めるようになったら標準の型(`JsonWebKey` など)に戻す(手で書いた型の宣言の行末に、`TODO` のコメントを付けてある)。

## テーブル

auth の feature が持つテーブルは、`admin_user`・`passkey`・`session`・`passkey_enrollment` の4つ。書き込めるのは auth の feature だけ。

- **管理者は1人だけ**(ユーザーが決めた)。`admin_user` は WebAuthn の `user.id`(user handle)を置くためにあり、行は1つに限る。`id` を 1 に固定する CHECK で、2つめの行を DB が断る。user handle は 16 バイトの乱数で、個人の情報を含めない。
- `passkey` の `id` は、資格情報の ID を、base64url(padding 無し)の正規形にした文字列。ログインでは、届いた ID を一度バイト列に戻し、同じ形に直してから引く。書き方が食い違うと、保存した ID でパスキーを引けない。
- `signCount` は uint32 なので、PostgreSQL の `integer`(符号付き32ビット)に収まらない。`bigint` にし、CHECK で 0〜4294967295 に絞る。
- AAGUID は `uuid`、transports は `text[]`、公開鍵は COSE_Key のバイト列のまま `bytea` に置く。
- `session` と `passkey_enrollment` には、token の secret の SHA-256 だけを置く。token そのものを持つのは、Cookie(セッション)と、コマンドの出力(登録用 URL)だけ。
- 管理者の行を消すと、パスキー・セッション・登録用の token も消える(`on delete cascade`)。
- 管理者が1人なので、索引は主キーと一意の制約だけにする。行の数はセッションの上限(後述)と、パスキーの数(管理者が自分で足すもの)で小さく保たれる。
- セッションは、どのパスキーでログインしたかを持たない。パスキーを消したときは、今のセッションのほかをすべてログアウトさせる(「パスキーの管理」)。

## origin と RP ID

- 管理画面の origin(`AUTH_ORIGIN`)と RP ID(`AUTH_RP_ID`)は環境変数で持ち、起動時に確かめる。RP ID が origin のホストか、その上位のドメインでなければ、ブラウザがパスキーの操作を断る(SecurityError)ので、起動しない。本番のドメインを変えると、パスキーの登録し直しが要る。
- origin は `https://example.com` のように、パスや末尾の `/` を付けない形だけを受け付ける。clientDataJSON の origin とは文字列で照らし合わせるので、書き方の揺れを起動の時点で止める。
- http は localhost(`*.localhost` も)だけを受け付ける。ブラウザは、それ以外の http でパスキーを使わせない。
- 既定値は持たない。本番で設定し忘れたときに、開発の値で起動させない。

## token(`secret-token/`)

セッションの Cookie と登録用 URL には、`{id}.{secret}` の形の token を入れる。ID は 16 バイト、secret は 32 バイトの乱数の base64url(padding 無し)。

- DB には ID と、secret の SHA-256 だけを置く。DB が漏れても、そこから token は作れない。secret は総当たりできない長さの乱数なので、パスワードのような遅いハッシュは要らない。
- secret はバイト列に戻さず、届いた文字列のままハッシュにする。base64url の最後の1文字は余りのビットを持ち、戻すと違う文字列が同じバイト列になる。
- secret のハッシュは定数時間で比べる。ふつうの比較は最初に違ったバイトで止まるので、かかる時間から合っている所を推し量られうる。
  - Node の `timingSafeEqual` ではなく、Web 標準だけで書いた比較(`equal-secret-hashes.ts`。全バイトの XOR を集め、途中で抜けない)を使う。feature のコードは Web 標準で書き、Bun や Node の API を platform に閉じ込める方針なので。比べるのは secret そのものではなく SHA-256 なので、JIT による小さな時間の差が残っても、そこから secret を推し量るには SHA-256 の原像が要る。長さは常に 32 バイトで秘密ではないので、長さが違えばすぐに false を返す。

## challenge(`challenge/`)

- challenge は 32 バイトの乱数で、プロセスのメモリの表に、用途と一緒に5分だけ覚える(ユーザーと決めた)。届いた応答の clientDataJSON から challenge を読み、表から取り出して消す。1回しか取り出せないので、以前の応答を送り直しても通らない。
- DB に置かないのは、ログインしていないリクエストで DB に書かないため。プロセスの中にあるので、server は1プロセスで動かす(server の「まだ決めていないこと」)。
- 用途(ログイン・登録用 URL からの登録・ログイン中のパスキーの追加・再認証)を一緒に覚え、取り出すときに照らし合わせる。登録用 URL の challenge は token の ID に、追加と再認証の challenge はセッションの ID に結びつけ、ほかの token やセッションでは使えない。用途が違っても、届いた challenge は使い切る。
- 表の大きさに上限(1万)を置き、満杯なら古いものから捨てる。ログインしていないリクエストでメモリを使い切られないようにし、新しいリクエストは断らない。表を埋めにくるリクエストが捨てさせるのは主に自分の出させた分で、正しい利用者の challenge を答えるまでに押し出すには、その間に上限の数を出させる速さが要る。
- 表は、届いた文字列そのもので引く。base64url には、末尾の余りのビットや `=` の padding だけが違う、同じバイト列に戻る書き方があるが、表のキーは正規形なので当たらない。仕様の手順(`verifyRegistration`・`verifyAuthentication`)も challenge を照らし合わせ直すので、二重の守りになる。
- IP ごとの回数の制限は、本番の置き場所と一緒に決める(server の「まだ決めていないこと」)。

## セッション(`session/`・`current-session/`)

- 使わないまま7日で切れ、使い続けてもログインから30日で必ず切れる(ユーザーが決めた)。使わないままの期限だけにすると、ときどき使えば永久に続く。
- 最後に使った日時と Cookie は、1時間に1回だけ書き直す。リクエストのたびに DB へ書かないため。Cookie の `Max-Age` は、書き直した時点からセッションが切れる日時までにし、DB の期限と同じ時刻に切れるようにする。
- 1人の管理者が持てるセッションは10個まで。ログインのたびに、切れたセッションを消し、新しい順に9個だけ残してから作る。Cookie を持たない端末からログインするたびに行が増え続けるのを防ぐ。
- 同じブラウザでログインし直したら、Cookie にあった前のセッションを消す(ID と secret のハッシュの両方が合う行だけ)。消さないと、Cookie から外れた行が切れるまで残る。
- 「すべてのセッションからログアウトする」は、今のセッションも含めて、管理者のセッションの行をすべて消し、今のブラウザの Cookie も消させる(ユーザーが決めた)。セッションの一覧は作らず、User-Agent も保存しない。
  - 今のセッションも消すのは、漏れた Cookie が今のブラウザのものでも、確実に使えなくするため。今の token を残すと、それを盗んだ人のログインが続く。
  - 誰も締め出されない(パスキーでログインし直せる)ので、再認証は求めない。同時に2つのセッションから求められても、どちらも消えてよいので、残すセッションを守る仕組みも要らない。
- 同じサイトの別の origin(`blog.example.com` など)のページは、ブラウザに、`SameSite=Strict` の Cookie を付けたリクエストを送らせることができる。GET は Origin の確認を通らないので、`Sec-Fetch-Site` が `same-origin` でなければ、無いときも含めて、GET でも断る(`procedures.ts`)。ほかのページに、セッションの期限を延ばさせない。対応するブラウザ(最新の Chrome と WebKit)はどれも `Sec-Fetch-Site` を付け、ブラウザでない client は管理用 API と認証用 API を呼ばない。
  - アドレスバーから API を開く GET(`none`)も断る。管理用 API は、管理画面から fetch で呼ぶもの。
  - 断ったときは、Origin と `Sec-Fetch-Site` をログに書く。
- Cookie は `HttpOnly`・`SameSite=Strict`・`Path=/`。管理画面は同じ origin の SPA で、ほかのサイトからのリンクで開いても、静的ファイルに Cookie は要らない。
  - https では名前を `__Host-analemma_session` にして `Secure` を付ける(ユーザーと決めた)。ブラウザは `__Host-` の Cookie を、`Secure`・`Path=/`・`Domain` 無しで書かれたときしか受け付けない。RP ID を上位のドメインにしたときに、ほかのサブドメインのページが `Domain` 付きで同じ名前の Cookie を書き、攻撃する側のセッションを、管理者に使わせること(ログインの CSRF)を防ぐ。
  - 開発の http の localhost では `analemma_session` にし、`Secure` を付けない。`__Host-` の Cookie には `Secure` が要り、http の localhost で `Secure` の Cookie を受け付けるかは、ブラウザによって違う。
- 確認できなかった Cookie(形が違う・知らない・secret が違う・切れた)は、401 の応答で消させる。切れた行はその場で消す。
- 期限を延ばす UPDATE は、最後に使った日時を進めるときだけ書く(`last_used_at < now`)。切れた行を消す DELETE も、DB の行がまだ切れているときだけ消す。同時のリクエストの片方が延ばした直後に、古い行を読んだもう片方が、延ばしたセッションを消したり、最後に使った日時を戻したりしないように。

## 登録用 URL(`enrollment/`)とコマンド

- 最初のパスキーの登録と、パスキーを全部失ったときの復旧は、server のコマンド(`bun run passkey:enroll`、`src/enroll.ts`)が出す1回きりの登録用 URL で行う(ユーザーが決めた)。誰でも登録できる仕組みは作らない。コマンドを動かせるのは server を動かせる人だけなので、それで管理者だと見なす。
- 登録用 URL は10分だけ使える。コマンドで出してからブラウザで開き、パスキーを作るまでの時間。新しい URL を出すと、前の URL は使えなくなる。登録に成功したら token の行を消し、1回きりにする。登録の options を取っただけでは使い切らない(パスキーの作成を取り消しても、やり直せるように)。資格情報を受け付けなかったときも使い切らない。
- URL は `{AUTH_ORIGIN}/enroll#{token}`。token は `#` の後ろに置き、server のアクセスログや Referer に残さない。管理画面の登録の画面(`/enroll`)を作るときに、この形に決めた(`apps/admin/DECISIONS.md`)。
- コマンドは登録用 URL だけを標準出力に書き、説明とログは標準エラーに書く。ログには token の ID と期限だけを書き、secret は書かない。
- 管理者の行(user handle)は、最初に登録用 URL を出すときに作る。登録用 URL からの登録が成功したら、そのままログインさせる。
- 復旧のときも、登録済みのパスキーを登録の options の `excludeCredentials` に並べる。手元に残っている認証器で、同じ管理者の2つめのパスキーを作らせないため。

## ログイン(`login/`)

- discoverable なログイン(`allowCredentials` は空)にする。認証器が、このサイトのパスキーから利用者に選ばせる。管理者のユーザー名は無い。
- options は `residentKey: "required"`・`userVerification: "required"`・`attestation: "none"`。timeout は challenge の寿命と同じ5分。
- 検証の順は、clientDataJSON を読む → challenge を取り出す → 資格情報の ID でパスキーを引く → userHandle を照らし合わせる → 仕様の手順で署名を確かめる。パスキーを引く前に challenge を取り出すので、知らないパスキーの試みでも challenge は使い切られる。
- 資格情報の ID と userHandle は、一度バイト列に戻してから、base64url の正規形に直して引く。書き方が揺れても、保存した ID と照らし合わせられるように。
- 知らないパスキーは `UNKNOWN_CREDENTIAL`、手順に合わない応答は `INVALID_CREDENTIAL` と分けて返す。管理画面で「このパスキーは消されている」と伝えられるように。
- `signCount` が戻っても拒まず、logger に警告を書く。保存した `signCount` は下げない(SQL の `greatest` で、届いた値と保存した値の大きい方を書く)。戻った値で上書きすると、複製された認証器が次からの比べる基準を下げられ、本物の認証器での後退が見えなくなる。
- BE が登録したときと違っても拒まず、logger に警告を書く(「登録とログイン」)。保存した BE は書き換えない。
- 署名を確かめた後、セッションを作るトランザクションの中で、そのパスキーの行がまだあることを確かめる(ID と公開鍵で照らし合わせる)。確かめている間に別のセッションからパスキーが消されたら、セッションを作らずに `UNKNOWN_CREDENTIAL` を返す。

## 再認証(`current-session/`)

- パスキーの追加と削除の前に、今のパスキーで確かめ直させる(再認証)。追加は Codex のレビューで見つかり、削除はユーザーが決めた。
  - 追加:漏れたセッションの Cookie を持つ人が自分のパスキーを足すと、ログアウトの後も、期限の無いログインの手段が残る。足すときの UV は、新しい認証器を持つ人を確かめるだけで、管理者であることは確かめない。
  - 削除:漏れた Cookie を持つ人に、管理者のパスキーを消させない。
  - 名前の変更と、すべてのセッションからのログアウトには求めない。どちらも、ログインの手段を増やしも減らしもしないため。
  - デプロイ用のトークンの発行にも求める。ログアウトの後も残る手段を増やすのは、パスキーの追加と同じため(`src/features/deploy-tokens/DECISIONS.md`)。
- 再認証の options は `admin.session.reauthenticationOptions` が返し、challenge を求めたセッションに結びつける。再認証を求める操作で、options を取る procedure を1つにそろえる。パスキーの追加の options(`admin.passkeys.registrationOptions`)は、登録の options だけを返す。
- 操作のリクエストに、再認証の資格情報(`assertion`)を一緒に送らせる。再認証の結果をセッションに覚えないので、1つの再認証で操作できるのは1回だけで、再認証と操作の間に別の操作を挟めない。
- 再認証が通らなければ `REAUTHENTICATION_FAILED` を返し、logger に、求めた procedure と理由を書く。
- 操作と同じトランザクションの中で、管理者の行のロックを取り、求めたセッションがまだあることを、行の共有ロック(`FOR SHARE`)を取って確かめる。確かめている間にログアウトなどでセッションが消されていたら、操作せずに `UNAUTHORIZED` を返す。再認証に使ったパスキーの `signCount` と使った日時も書き、そのパスキーが消されていたら `REAUTHENTICATION_FAILED` を返す。
- 再認証に使ったパスキー自身も消せる(ほかに1つ残れば)。

## パスキーの管理(`passkeys/`)

- 一覧・追加・名前の変更・削除を、管理用 API に置く(ユーザーが決めた)。一覧の出力は、名前・登録した日時・最後に使った日時・同期されているか(BS)だけにし、公開鍵や `signCount` は出さない。
- 追加の challenge は、options を求めたセッションに結びつける。
- 足す・消すには、再認証が要る(「再認証」)。
- 最後の1つは消せない(ユーザーが決めた)。全部消すと、コマンドで復旧するしかなくなる。数えてから消すまでの間に、もう1つが消されないよう、管理者の行のロックを取ってから数える(「同時の書き込み」)。
- パスキーを消したら、同じトランザクションで、今のセッションのほかをすべてログアウトさせる(ユーザーが決めた)。なくした端末のパスキーを別の端末から消しても、なくした端末のログインが最長30日残ってしまうため。セッションは、どのパスキーでログインしたかを持たないので、消したパスキーのものだけを選べない。消せなかったとき(最後の1つ・無いパスキー)は、ログアウトさせない。
- 名前は前後の空白を落として1〜64文字で、制御文字(NUL・改行など)は使えない。PostgreSQL の `text` は NUL を保存できず、そのままでは入力の誤りが 500 になる。登録と名前の変更で、同じスキーマを使う。
- transports は、仕様にある値(`usb`・`nfc`・`ble`・`smart-card`・`hybrid`・`internal`)だけを重ねずに残す。個数と型だけを見ると、400 KB の文字列でもそのまま保存されてしまう。値は参考のためだけに持つので、知らない値は捨てる。contract でも、1つ32文字・16個までに絞る。

## 同時の書き込み

次の操作のトランザクションは、先に管理者の行のロック(`FOR NO KEY UPDATE`)を取る(`admin-user/lock-admin-user.query.ts`)。管理者は1人なので、これらの書き込みは1つずつ進む。

- ログイン(パスキーの使用を書き、セッションを作る)と、登録用 URL からの登録:セッションの整理から挿入までが重ならず、10個を超えない。
- 登録用 URL を出すこと:コマンドを同時に動かしても、使える URL は1つだけになる。
- 再認証を求める操作(パスキーの追加と削除):最後のパスキーを数えてから消すまでの間に、もう1つが消されない。

ログアウト・すべてのセッションからのログアウト・名前の変更・期限の延長と、切れたセッションを消すことは、管理者の行のロックを取らない。どれも1つの文か条件付きの文で済み、重なっても結果は食い違わない。ただし、すべてのセッションからのログアウトは、デッドロックを防げない(「割り切ったこと」)。

- デッドロック:ログインはパスキーの行を書いてから、セッションの外部キーの検査で管理者の行に `FOR KEY SHARE` を取る。削除が管理者の行に `FOR UPDATE` を取ってからパスキーの行を待つと、互いに待つ。ロックを取る順を「管理者の行が先」にそろえ、外部キーの検査とぶつからない `FOR NO KEY UPDATE` を使う。

## 監査の記録

登録・ログイン・ログアウト・すべてのセッションからのログアウト・パスキーの追加と名前の変更と削除・断ったログインと登録と再認証・`signCount` の後退と BE の変化・管理画面の origin からでないリクエストを、context の logger に書く(ユーザーと決めた。まずは logger に出す。残し方は server の「まだ決めていないこと」)。パスキーとセッションの ID は書くが、token の secret・公開鍵・個人の情報は書かない。

## テスト

- WebAuthn の手順は、純粋な関数の単体テストで確かめる。セッション・ログイン・登録用 URL・パスキーの管理は、API 越しに確かめ、DB の中身を見ない。
- API 越しのテストは、`src/test-client/` のテスト用の認証器で、登録用 URL からパスキーを登録してログインする(`signInAsAdmin`)。管理用 API のほかの feature のテストも、これでログインしてから呼ぶ。
- テストの client は、ブラウザと同じく Set-Cookie を覚えて送り返す。別のブラウザを開けるので、すべてのセッションからのログアウトや、セッションの上限を確かめられる。
- 時刻は、テストの client に渡す clock で進める。セッションの期限や challenge の寿命は、本物の時間を待たずに確かめる。
- 想定外の失敗が 500 とログになることは、throw する clock で確かめる。セッションを続ける処理が、DB に問い合わせる前に時刻を読むため。

## 割り切ったこと

- **壊れた clientDataJSON**:clientDataJSON が JSON として読めないと、`JSON.parse` が throw し、500 と error のログ1行になる。ブラウザは壊れた clientDataJSON を作らず、細工したリクエストでだけ起きる。`auth.login.verify` はログインしていなくても呼べるので、誰でも error のログを出せる。error のログを監視で知らせるようにするときは、この失敗を除くか、IP ごとの回数の制限(server の「まだ決めていないこと」)と一緒に見る。challenge を取り出す前で DB にも触れないので、try/catch や `.catch()` で受け止めて、`Rejected` に変えることはしない(ユーザーが決めた)。
- **WebCrypto が読めない鍵**:登録で届いた鍵を WebCrypto が読めない(曲線の上に無い点など)と、throw して 500 とログ1行になる。本物の認証器は読める鍵しか作らず、細工したリクエストでだけ起きる。読めない理由が鍵の誤りか WebCrypto の障害かは、throw された値の型から見分けられないので、try/catch や `.catch()` で受け止めて、`Rejected` に変えることはしない(ユーザーが決めた)。
- **CBOR と DER の正規形でない形**:CBOR の最短でない整数の書き方、COSE_Key の余分な項目、DER の余分な先頭の 0 は受け付けている。仕様は CBOR の正規形でない形を拒むことを SHOULD にしているが、これらから署名を偽造できる経路は無い(Codex のレビューでも見つからなかった)。受け付ける形を減らすなら、ここを絞る。
- **CBOR の UTF-8 でないキー**:map の2つのキーが、どちらも UTF-8 でない別々のバイト列だと、どちらも置換文字になり、重なったキーとして拒まれる。仕様に合う認証器は UTF-8 のキーしか書かず、細工した入力でだけ起きる。拒むだけで、困るのは細工した側なので直さない。
- **RP ID の public suffix**:RP ID が Public Suffix List の public suffix(`co.uk` など)かは確かめない。そうした RP ID はブラウザが断るが、起動の時点では気づけない。リストへの依存を持つほどの守りではないので、受け入れる。
- **challenge の再起動**:challenge はプロセスのメモリにあるので、server を再起動すると消え、その間に始めたログインや登録は `CHALLENGE_EXPIRED` になる。利用者がやり直せば済むので、受け入れる。
- **使わないままの期限の誤差**:最後に使った日時を1時間に1回だけ書き直すので、使わないままの期限は、最後に使ってから「7日から最大1時間を引いた」ときに切れる。最大1時間早く切れるだけで、ログインし直せば済むので受け入れる。
- **ミリ秒の差で重なる同時のリクエスト**:管理者は1人なので、2つのリクエストがミリ秒の差で重なったときの次の食い違いは直さない。どれもデータは壊れず、起きるのは、やり直せば済む失敗か、警告の1回の見落としか、ロックを待った分だけ期限を越えて通る登録だけ。新しく見つかった重なりは、データが壊れないことを確かめてから、ここに足す。
  - 片方が期限を延ばした直後に、古い行を読んだもう片方が、行が残っていても 401 を返して Cookie を消させる。401 を返す側が消すのは、DB の上でもまだ切れている行だけなので、延ばした行は消えない。ログインし直せば済む。
  - パスキーの追加と削除で、確かめている間にセッションが消されていると、`UNAUTHORIZED` を返すが、Cookie は消させない。パスキーは足しも消しもしない。セッションはもう無く、Cookie は次のリクエストの 401 で消える。
  - すべてのセッションからのログアウトは、管理者の行のロックを取らずにセッションの行を消すので、パスキーの削除やログインと重なると、ロックを取る順が食い違い、PostgreSQL がデッドロックとして片方を止めて 500 になる。止められたトランザクションは丸ごと取り消されるので、消すはずのセッションが黙って残ることは無く、利用者がやり直せば済む。
  - 登録用 URL の期限は、登録のリクエストを受けた時刻で判断し、DB のロックを待つ間に10分を越えても通す。越えるのは、同時の書き込みのロックを待った分だけで、通るのは期限の前に届いた登録だけ。
  - `signCount` の警告は、ロックを取る前に読んだ値と比べるので、同時のログインでは、戻ったことを見落としうる。見落とすのは警告だけで、DB の `signCount` は大きい方を残すので戻らない。ログインできるかどうかも変わらない。
- **Cookie の `Max-Age` のずれ**:Cookie の `Max-Age` は、リクエストを受けた時刻から数える。応答が遅れた分(数秒)だけ、Cookie が DB の期限より長く残ることがあるが、server はその Cookie を断るので受け入れる。
- **応答が逆の順で届くとき**:期限を延ばした応答と、ログインし直した応答が逆の順で届くと、新しい Cookie が古い token で上書きされうる。管理画面がログインの最中にほかの管理用 API を呼ばなければ起きない(`apps/admin/DECISIONS.md`)ので、server では防がない。
- **連打したとき**:同じ操作を続けて送ると、先のリクエストで成功しても、後のリクエストが失敗を返すことがある(使い切った再認証の資格情報、消えたセッションなど)。結果は先のリクエストのとおりで、表示が食い違うだけ。管理画面で、送信中はボタンを無効にする(`apps/admin/DECISIONS.md`)。
- **パスキーの ID の長さ**:名前の変更と削除の入力の、パスキーの ID には長さの上限が無い。本文の大きさの上限(1MB)で抑えられ、知らない ID は `NOT_FOUND` になるだけなので、受け入れる。
- **登録用 URL で登録したときの前のセッション**:登録用 URL から登録してログインしたとき、同じブラウザの Cookie にあった前のセッションは消さない(パスキーでのログインでは消す)。前のセッションは、切れるか、セッションの上限で押し出されるまで残る。復旧はまれで、その Cookie はもうブラウザに無いので受け入れる。
- **消したパスキーの作り直し**:ログインや再認証を確かめている間にパスキーが消され、同じ ID と同じ公開鍵で行が作り直されたときは区別しない。認証器は登録のたびに新しい鍵を作るので、本物の認証器では起きない。
- **再認証と操作の組み合わせ**:再認証の資格情報と操作は、同じセッションの中なら組み合わせを問わない。options を2回取ると、1回目の再認証と2回目の登録を組み合わせても通り、削除の前に取った再認証でパスキーを足しても通る。まだ使っていない再認証の応答を持つのは本人だけなので、受け入れる。
