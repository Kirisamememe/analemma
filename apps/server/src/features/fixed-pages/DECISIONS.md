# 決めたことと理由(fixed-pages の feature)

固定ページ(About・Colophon など)を扱う。フェーズ1は固定ページだけを作る(ユーザーと決めた。開発の基盤の効果を、一番シンプルなもので確かめるため)。

## 列と JSONB

- 固定ページは、メタデータ(slug・タイトル・種類・公開状態・並び順・日時)を列に、中身を JSONB に持つ(ユーザーと決めた)。中身の形は種類ごとに決まっていて、保存のときに必ず種類の定義で検査する。自由な JSON は持たない。
- 種類は、ページを作るときに選び、後から変えない。変えると、中身を別の定義で検査し直すことになり、どちらの定義のデータを残すかを決める必要が出る。
- slug は、種類ごとではなく、固定ページの全体で1つにする。公開サイトの URL に使いやすいように。
- ID は PostgreSQL 18 の `uuidv7()` で作る。
- 公開 API は、種類と slug で引き、種類が違えば無いものとして返す。公開サイトは、ページの種類を知ったうえで引き、その種類の定義から推論した型で中身を受け取るので、違う種類のページを返すと、型と中身が食い違う。

## 保存と検査

- 中身の検査は、kinds の feature の `checkContent`(contract の `toContentSchema`)で行う。定義に無いキーは、検査で落とさずに残す。項目を消した定義を受け取っても、データを JSONB に残し、古いサイトに戻したときにデプロイを止めないため(ユーザーと決めた)。
- 管理用 API の `get` は、定義に無いキーも含めた中身を返す。管理画面は、フォームに出さないキー(定義に無いキー。`group` の値の中にあるものも)を、そのまま送り返す。送り返さないと、書き換えたときに消える。server は丸ごと置き換えるだけで、保存済みのキーを引き継がない。固定ページのフォームを作る PR で、送り返すことを管理画面のテストで確かめる。
- 公開 API は、今の定義にある画像の項目を解き、ほかの値は定義に無いキーも含めてそのまま返す。形をそろえるのは公開サイトの client で、自分の定義で検査し、定義に無いキーを取り除く(`packages/client/DECISIONS.md`)。
  - デプロイでは、新しい定義を送ってから新しいサイトに切り替えるので、項目を消した定義を受け取った後も、切り替えるまでは古いサイトが動いている。CMS が中身から項目を取り除くと、古いサイトの client が、必須の項目が無いとして断り、ページを読めなくなる。切り替えに失敗したときも、読めないままになる(Codex のレビューで見つかった)。
- 中身を書くのは、`editing/queries/save-fixed-page.query.ts` の `saveFixedPage` だけにする(作成と書き換えの両方)。編集履歴を足すときは、ここで同じトランザクションに写しを書く(ユーザーと決めた。編集履歴そのものは後で足す)。
- 中身が定義に合わないときは、`INVALID_CONTENT` に、合わない場所(キーと添え字の並び)と zod の issue の code を、20件まで添える。管理画面が、フォームのどこに出すかを決められるように。
- 保存のときは、種類の行の共有ロック(`FOR SHARE`)を取ってから、定義を読んで検査する。定義を受け取る側は、種類の行に `FOR NO KEY UPDATE` を取ってから、既存のページを検査する。2つが重なっても、検査に使った定義と違う定義のもとで、ページが保存されることは無い。
- 書き換えでは、固定ページの行のロックを取ってから、種類の行のロックを取る。定義を受け取る側はページの行のロックを取らないので、順が食い違っても、互いに待ち合わない。

## 画像の項目

- 使用中の画像も非公開にでき、削除できる。画像が取れなくなっても、必須か任意かによらず固定ページを公開し続ける。未入力の任意の項目は省く。
- 中身には画像の ID を文字列で保存する。作成・書き換えでは ID の形と必須の指定だけを検査する。画像を削除した後も、管理者がその ID を残してほかの項目を編集できるようにするため。
- TODO: 公開 API の値を、取得できれば `{ available: true, image }`、非公開か、ID に対応する画像が無ければ `{ available: false }` とする形で確定する。公開サイトが代わりの表示を選べるようにし、非公開と削除は区別しない。入れ子も含めて画像の ID をまとめ、画像の公開 API と同じ形にする。

## 公開状態

- 新しいページは、公開していない状態で作る。データが入って公開するまで、公開 API からは見えない(ユーザーと決めた)。見つからないものと公開していないものは区別しない。
- 公開状態は `publishedAt` の有無で持つ。公開状態の判定は、`published/queries/published-fixed-pages.query.ts` の `isPublished`(行を見る)と `matchPublished`(SQL の条件)だけで行う。
- 公開し直しても `publishedAt` は変えず、非公開に戻すと消す。公開した日時は公開サイトに出しうる値で、公開を押し直すたびに変わると困る。
- `updatedAt` は、タイトル・slug・中身を変えたときだけ進め、公開と並び順の変更では進めない。公開サイトに「最終更新」として出せるように。同じ値のまま保存し直したときも進めない(書き換えの UPDATE の中で、前の値と比べる。Codex のレビューで見つかった)。

## 並び順

- 並び順は、種類ごとではなく、すべての固定ページを1つの列で並べる。新しいページは最後に付く。
- 並べ直しは、送られた ID の並びを `jsonb_array_elements_text` で表にして、1文の UPDATE で振り直す。ページごとに UPDATE を流さない。
- 並べ直しでは、すべてのページの ID を、並べたい順に送らせる。ID は、大文字で書いても同じ ID として照らし合わせる(PostgreSQL は小文字で返す)。今あるページと1つでも食い違えば、`ORDER_MISMATCH` で断る。管理画面が古い一覧のまま並べ直して、ほかで作ったページの位置を黙って決めてしまわないように。確かめる前に、すべての行のロックを ID の順に取る。
- 並び順の値が重複したときは(「割り切ったこと」)、作った日時と ID の順に並べる。
- 一覧(管理用 API と公開 API)と並べ直しの応答は、中身(JSONB)を読まない。

## 削除

- 固定ページの削除は、物理削除にする(ユーザーが決めた)。消したページは、公開 API からも管理用 API からも無くなる。編集履歴を足すときは、消したページの履歴をどうするかも一緒に決める。

## まだ作っていないもの

- ビジネスイベント(キャッシュの無効化など)は、dispatcher を作るときに足す。今は、書き込んだ後に何も配らない。
- canonical URL は、公開サイトが固定ページをどのパスに置くかが決まってから、mapper で作る。今は slug だけを返す。

## 割り切ったこと

- **書き換えの slug の競合**:書き換えで slug を変えるときは、ほかのページに使われていないかを確かめてから書く。同時に2つのページを同じ slug に書き換えると、後の方が一意の制約で失敗し、500 とログになる。管理者は1人で、ミリ秒の差で同じ slug を2つのページに付けることはまず無い。作成の競合は `ON CONFLICT DO NOTHING` で `SLUG_TAKEN` にしている。
- **並び順の値の重複**:新しいページの並び順は、今の最大の値に1を足して決める。同時に2つ作ると同じ値になるが、作った日時と ID の順に並ぶだけで、並べ直せば直る。
- **並べ直しと作成の重なり**:並べ直しがロックを取った後に作られたページは、並べ直しの確かめから漏れる。並べ直しは成功し、そのページは作ったときの並び順の値のまま残る。値が重複していた後だと(上の「並び順の値の重複」)、最後ではなく途中に入りうる。管理者がもう一度並べ直せば直る。
- **1,000件を超えたときの並べ直し**:並べ直しの入力は1,000件までなので、固定ページが1,000件を超えると並べ直せない。個人サイトの固定ページはそこまで増えないので受け入れる。
- **同時の書き込みのテスト**:保存と種類の定義の受け取りが重なったときに、ロックで順番が決まることは、テストで確かめていない。2つのトランザクションを決まった順に重ねる仕組みが要る。ロックの取り方は、このファイルの「保存と検査」に書いた。ロックの順が崩れると、ミリ秒の差で重なった保存と定義の受け取りで、新しい定義に合わないページが残りうる。その種類の次の定義の受け取りで、そのページは破壊的変更として一覧に出て、管理画面で直せるので、確かめる仕組みを作るほどではない。
- **定義に無いキーの値の `\u0000` と、対になっていないサロゲート**:定義に無いキーは検査しないので、その値に `\u0000` か、対になっていないサロゲートがあると、PostgreSQL が jsonb への保存を断り、500 とログになる。管理画面はフォームに出さないキーを送り返すだけで、細工したリクエストでだけ起きるので受け入れる。
- **定義を送ってからサイトを切り替えるまで**:画像の ID を持つテキストを同じキーの画像の項目に変えると、定義を送った時点で公開 API の値が文字列からオブジェクトに変わり、古いサイトはページを読めなくなる。画像を別のキーに足し、サイトの切り替えまで元のキーと値を残す。切り替える前に管理者が、新しい定義でだけ許される形に中身を書き換えると(必須から任意にした項目を空にするなど)、古いサイトはそのページを読めなくなる。この間の編集による失敗は、新しいサイトに切り替われば読めるので受け入れる。
- **定義から消した画像の項目**:公開 API は保存済みの ID を返すので、内部用のポートに届く呼び出し元には非公開画像の ID も見える。消した項目の型は保存しておらず、UUID を入れたテキストと区別できない。古いサイトが使うテキストを保つため、値の形だけで置き換えない。画像の取得と配信には引き続き公開状態の判定を使う。
