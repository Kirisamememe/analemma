## 見る範囲

フェーズのブランチに入った、いくつもの子のブランチの変更を合わせたときの、つながりと一貫性。子のブランチは、それぞれ観点ごとにレビューしてあるが、どのレビューも1つの PR の中しか見ていない。どの PR から来たかは、merge commit のメッセージか、squash で入れたコミットの1行目の末尾の ` (#番号)` で分かる。rebase で入れた PR には番号が残らないので、確かめきれないときはそう書く。

- PR をまたいだ食い違い:前の PR で決めたことを、後の PR が黙って覆していないか。片方の PR だけが直り、もう片方が古い前提のまま残っていないか。
- 同じ概念の重複:同じことをする関数・型・スキーマ・定数・部品が、別の場所に別の名前で作られていないか。同じ形を手で写していないか。
- 文書どうしの一致:`DECISIONS.md` どうし、`DECISIONS.md` と `AGENTS.md`、それらと `GLOSSARY.md` が食い違っていないか。同じ概念を、PR によって違う名前で呼んでいないか。用語集に足すべき概念の名前が無いか。「割り切ったこと」どうしが重なったり矛盾したりしていないか。
- 設計のずれ:feature の分け方、server・contract・client・管理画面の役割と依存の向き、失敗の扱い方、テストの書き方が、PR によって違っていないか。ブランチの中身の直下の `AGENTS.md` の設計の原則から、全体として外れていないか。

## 見ない範囲

- 1つの PR の中で完結する指摘。子のブランチの観点ごとのレビューで見てある。
- lint・型検査・テスト・hook が止めるもの。
- 好みの違いだけの、書き方の不ぞろい。
