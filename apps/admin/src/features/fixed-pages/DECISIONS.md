# 決めたことと理由(管理画面の固定ページ)

## 一覧と並べ直し

- 画面は `/fixed-pages`(固定ページ)。並び順のまま、タイトル・公開状態・slug・種類のラベル・更新日時を出し、公開と非公開の切り替え・並べ直しを置く。削除は行に置かず、編集の画面にだけ置く(「編集の画面」)。見出しと、ページが無いときの欄に作成(`/fixed-pages/new`)への導線を、行に編集(`/fixed-pages/$id`)への導線を置く。
- 種類のラベルは、種類の一覧(`admin.kinds.list`)から引く。種類の一覧を読めないときや、一覧に無い種類のページでは、種類の名前を出す。種類は一覧の補足で、読めなくても固定ページの操作はできるので、一覧全体を失敗にしない。種類の一覧が届くまでは、一覧を出さずに読み込み中にする。先に名前で出すと、普段は名前がすぐラベルに替わってちらつく。
- query のキーは `["admin", "fixedPages", "list"]` と `["admin", "kinds", "list"]`(`list/fixed-pages-query.ts`。作成の画面の種類の選択も同じキーを使う)。保存の後のキャッシュの扱いは、「中身とフォーム」の最後の項目。
- 公開と非公開の切り替えは、戻せる操作なので、確認の Dialog を出さずにその場で送る。成功を Toast で知らせ、一覧を取り直す。ほかで消えたページの操作は `NOT_FOUND` になるので、一覧を取り直したことと一緒に Toast で知らせる。想定外の失敗でも一覧を取り直す。変えられてから応答だけが失敗したときに、一覧を server に合わせるため。
- 「公開する」は塗りのボタン(`primary`)、「非公開にする」は枠のボタン(`secondary`)にする。役割が違うので、幅だけでなく見た目でも分ける(ユーザーが決めた)。
- 並べ直しは、置いたらすぐに送り、保存のボタンを置かない。全部の ID を並べた順に送る。送っている間は、置いた順に並べ、並べ直しを止め、一覧の上に保存していることを出す(行の中の操作は使える)。答えが届いたら一覧を取り直し、結果を Toast で知らせる。`ORDER_MISMATCH`(ほかで固定ページが増えたか減った)なら、取り直した一覧を出し、並べ直し直すよう知らせる。想定外の失敗なら、元の並びに戻して取り直す。

## 編集の画面

- 見出しの操作に、削除と保存を並べ、フォームの下にも保存を置く(長いフォームで、保存が一番下にしか無かった。ユーザーが決めた)。見出しをフォームの中に置き、上の保存も送信のボタンにする。作成の画面には削除を置かない。
- 削除のボタンは、ゴミ箱のアイコンだけにする(名前は「固定ページを削除」)。赤い「削除」のボタンは、タイトルを出した確認の Dialog の中にだけ置く(ユーザーが決めた)。削除は物理削除で戻せないので確かめる。
- 削除できたら、一覧を取り直してから一覧に戻り、Toast で知らせる。取り直す前に戻ると、持っていた一覧に削除したページが一瞬出る(`apps/admin/DECISIONS.md` の「server の API の呼び方」)。応答が届いたときに編集の画面を閉じていたら、一覧へは移らない。移ると、移った先の画面で離れる前の確かめを飛ばし、そこで入力した値を消す。ほかで消えていたら(`NOT_FOUND`)、Dialog の中で知らせ、削除のボタンを止める。想定外の失敗も Dialog の中で知らせ、送り直せるように Dialog を開いたままにする。前の送信の結果は、Dialog を開くときに消す。削除の確認のボタンは、Dialog を閉じ始めた後の押下では送らない(タッチの長押しの遅れた click。`src/ui/DECISIONS.md` の「割り切ったこと」)。パスキーの削除と違い、再認証の OS の画面で止められないため。
- 保存していない変更があるまま画面を離れるときは確かめる(ユーザーが決めた)。管理画面の中の移動は Dialog で確かめ、タブを閉じる・読み込み直すときはブラウザに確かめさせる。変更があるかは、開いたときの値(保存できたら、送った値)と今の値から、保存で送る slug・タイトル・中身を作って比べる。入力して元に戻した値や、送らない未入力の違いでは確かめない。保存を送っている間は、保存できるとは限らないので確かめる。保存できた後の移動(作成から編集の画面へ)と、削除した後の移動は確かめない。
- 保存の想定外の失敗(通信の失敗など)は、送り直せば済む一時的な失敗なので、Toast(`danger`)で知らせる。server が断った値(`SLUG_TAKEN`・`INVALID_CONTENT`)と、ページや種類が無いことは、直すまで残るフォームの状態なので、欄とフォームの `Notice` に出す。

## 中身とフォーム

- フォームの最上位の段・group・repeat の各要素は、それぞれの段で、項目の値と、定義に無いキーの値を分けて持つ。server は中身を丸ごと置き換えるので、定義に無いキーも元の段に戻して送る。キーと値の組から `Object.fromEntries` でオブジェクトを作り、`__proto__` もその名前のキーとして扱う。
- text・longText・url の未入力は空の文字列、number・date・select の未入力は `null` にする。これで `0` も入力した値として扱える。boolean はいつも値を持ち、新しい固定ページでは項目の既定値から始める。
- 保存した中身の値は、contract のスキーマと select の選択肢で確かめる。boolean は保存済みの真偽値をそのまま表示し、値が無いか真偽値以外なら項目の既定値を表示する。ほかの項目は、値が無いときや定義と食い違うときに未入力に戻す。server は取得した中身をそのまま返し、保存時に値の無い真偽値へ既定値を入れる。公開サイトの client は、ページを読むときに既定値を補う。object でない repeat の要素も位置を保ち、管理者がその場所で直せるようにする。
- 送るときは未入力の項目のキーを省き、必須かどうかの検査は server に任せる。必須の group は空でも送り、内側の項目に issue が付くようにする。必須の repeat は要素が無ければ空の配列を送る。任意の group を送るのは、内側に入力した値・repeat の要素・定義に無いキーのいずれかがあるときだけ。既定値のままの boolean は入力に数えない。内側の必須の group・repeat が空であることだけでは、外側の group を入力したことにはしない。
- repeat の要素にはフォームを作るときに `crypto.randomUUID()` で ID を付ける。要素を動かしても値と ID は一緒に動き、保存には値だけを使う。issue の添え字は送ったときの並びで ID に読み替える。値を持つ項目・group・repeat・repeat の要素までたどれた issue はその場所に結びつけ、結べない issue は `unbound` として別に返し、画面がフォーム全体の誤りとして出せるようにする。
- TanStack Form には、入力値と repeat の ID の並びを別々に持たせる(`editor/flat-content.ts`)。場所には項目のキーと要素の ID を `/` でつないで使う。`ContentForm` は再帰する型なので、そのまま TanStack Form の値にすると、field の名前の型(`DeepKeys`)が無限に展開されて型検査が止まる。添え字ではなく ID を名前に使うので、並べ替えても入力・誤りの知らせ・touched は同じ要素に残る。
- server が断った値(`SLUG_TAKEN` と、結べた `INVALID_CONTENT` の issue)は、`Form` の `validationErrors` で欄ごとに出し、その欄の値を変えたら消す。group・repeat・repeat の要素に結べた issue は、そのまとまりの見出しの下に出す。issue の文言は `code` から選び、zod の英語の `message` は出さない。誤りを出したら、最初の誤りの欄に focus を移す。
- 並べ替えで要素が端に着き、押したボタンが無効になったら、同じ要素の反対の向きのボタンに focus を移す(無効のボタンは focus を受け取れない)。削除した後は、次の要素の削除ボタンに、末尾なら追加ボタンに focus を移す。
- 送っている間も、入力欄は止めない。止めると、Enter で送ったときに focus が失われる。
- 編集の画面は、固定ページと種類の定義を、開くたびに読み直してからフォームを作る(`useApiQuery` の `discardWhenUnused`)。更新できたら、固定ページのキャッシュを更新の応答で差し替え、取り直すのは一覧だけにする。保存の後に取り直すと、取り直している間に画面を離れて戻ったときに古い値でフォームを作り、取り直しが失敗するとフォームが消える。

## 割り切ったこと

- **取り直しの失敗と重なり**:一覧の取り直しは、失敗しても呼び出し元に返さない(`invalidateQueries` の既定)。`ORDER_MISMATCH` や `NOT_FOUND` の後の取り直しが失敗すると、一覧は読み込めない知らせに替わるのに、「一覧を読み込み直しました」と知らせる。また、並べ直しの後の取り直しの最中に、ほかの行の公開を切り替えると、先の取り直しが中断されて保存中の表示が消え、後の取り直しが届くまでの間(普段は数十ミリ秒)、保存する前の並びが出て、並べ直しを始められる。どちらも、書き込みと取り直しの両方が失敗するか、数十ミリ秒の間に操作を重ねたときだけ起き、次の取り直しで正しい一覧に戻る。取り直しの結果を書き込みの結果と別に扱う作りは、server の状態の包み(`src/api/server-state/`)ごと直す必要があり、手間に見合わないので受け入れる。
- **削除の後の取り直しを待つ Dialog**:削除が成功しても、一覧を取り直すまで Dialog は送信中のままで、閉じられず、一覧にも戻らない。パスキーの削除と同じ作りで、取り直しは普段は数十ミリ秒で終わる。
- **削除の後の取り直しと、ほかの取り直しの重なり**:一覧で公開を切り替えて応答を待つ間に、別のページを開いて削除すると、公開の切り替えの取り直しが、削除の後の取り直しを中断する。削除の側は取り直しを待たずに一覧へ戻り、公開の切り替えの取り直しが届くまで(普段は数十ミリ秒)、削除したページの行が出る。応答を待つ数十ミリ秒の間に、ページを開いて削除まで進めたときだけ起き、次の取り直しで正しい一覧に戻る。上の「取り直しの失敗と重なり」と同じく、server の状態の包みごと直す必要があるので受け入れる。
- **ログアウトとセッション切れのときの、離れる前の確かめ**:保存していない変更があるとき、ログアウトの後と、セッションが切れて(`UNAUTHORIZED`)ログインの画面へ移るときにも、離れる前の確かめが出る。セッションが切れたときは、入力を写し取ってから離れられる。「編集を続ける」を選ぶと、保存できない編集の画面に残り、次の操作で同じ確かめが出るので、「変更を破棄」で抜ける。ログアウトを送る前に確かめるには、ナビのログアウトと編集の画面の状態をつなぐ仕組みが要り、手間に見合わないので受け入れる。
- **保存を送っている間に離れたとき**:離れる前の確かめで変更を破棄しても、送った保存は取り消さない。届けば保存され、失敗すれば移った先の画面に失敗の Toast が出る。送信を中断するには、取得と保存の全体で進行中の要求を中断する仕組みが要り、起きるのは応答を待つ数十ミリ秒の間に離れたときだけなので受け入れる。
- 任意の group・repeat を空のまま保存してあった固定ページは、保存し直すとそのキーが消える。フォームではどちらも未入力として扱うので、空で保存されていたかを別に持つ理由が無い。
- 任意の group の中身が、既定値のままの boolean だけで保存されていた場合、保存し直すと group ごと省かれる。フォームは、既定値のままの場合と、管理者が既定値と同じ値を選んだ場合を区別しない。
- 保存した中身に無い項目も、フォームを作るときは値のスキーマで検査する(`safeParse(undefined)`)。repeat が1万要素あり、各要素に任意の項目が100個ある中身では、フォームを作る時間が約100ms 伸びる(Bun で計測)。個人サイトの固定ページの repeat はそこまで増えず、フォームを作るのは開くときの1回だけなので、受け入れる。
- 保存を送ってから応答が届くまでの間(普段は数十ミリ秒)に変えた入力は、次のように扱いが崩れる。どれも、その間に入力したときだけ起き、保存し直せば直るので受け入れる。
  - 作成できて編集の画面に移ると、その間の入力は消える。
  - 応答の誤りは送ったときの場所に付けるので、その間に直した欄に古い値の誤りが出る。その間に消した repeat の要素にだけ誤りがあると、保存できなかったことが出ない。
- 編集の画面を開き直したときに、前の応答を使い回すことがある。保存の応答が届く前に同じページを開き直すと、更新の前の値でフォームを作りうる。読み込みの応答が届く前に画面を離れて開き直すと、進行中の取得を使い回すので、その間にほかのタブで書き換えた値は入らない(取得に `AbortSignal` を渡していない)。どちらも、応答を待つ数十ミリ秒の間に開き直したときだけ起き、そのまま保存すると古い値に戻すが、管理者が自分で直前に書いた値なので気づける。直すには、取得と保存の全体で、進行中の要求を中断して待ち合わせる仕組みが要るので受け入れる。
- 保存の応答が届いたときに編集の画面を閉じていたら、固定ページのキャッシュを差し替えない。差し替えると、使う画面の無いキャッシュが既定どおり5分残り、開き直したときに、その間にほかのタブで書き換えた値を隠す。
- 年 `0000` の2月29日を中身に持つ固定ページは、編集の画面を描けずにエラーになる。日付の欄は年 `0000` を扱わない(`src/components/forms/DECISIONS.md` の「割り切ったこと」)。管理画面からは入らず、API へ直に送ったときだけ起きるので、日付の欄で年 `0000` を扱うと決めるまで受け入れる。
- 編集画面を開いたまま真偽値の項目の既定値をデプロイで変えると、まだ値の無いページでも、保存したときに画面に出ている変更前の値が書き込まれる。新しい既定値を使うには、保存する前に画面を開き直す。開いた後の定義まで追うには、グループや繰り返しの中も含め、各項目が保存済みか、管理者が編集したかを別に持つ必要がある。個人サイトで定義の変更とページの編集が重なるときに限られ、保存後も Checkbox で直せるため、画面に出ている値を保存する。
