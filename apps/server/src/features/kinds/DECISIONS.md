# 決めたことと理由(kinds の feature)

固定ページの種類の定義を、公開サイトから受け取って持つ。

## 種類の定義は、公開サイトのコードを正とする

- 種類は、公開サイト(Amayadori)のコードで、client の `defineKind` で定義する。型は TypeScript が定義から推論するので、型を書き出すコマンドは作らない(ユーザーと決めた)。
- 公開サイトの本番のデプロイのときに、client の CLI が、定義を JSON にして、デプロイ用 API(`deploy.kinds.push`)に送る。新しいサイトに切り替える前に送り、CMS が断ったらデプロイを止める。プレビューのデプロイからは送らない。
- CMS は受け取った定義を DB に持ち、ページの中身を保存するときの検査と、管理画面のフォームの自動生成に使う。種類を手で定義する画面は作らない。

## 定義の形(contract の `kinds/`)

- 項目の型は、テキスト・長いテキスト・数値・真偽値・日付・URL・選択肢から1つ・グループ・繰り返し(グループの一覧)。画像はフェーズ3、Markdown はフェーズ4で足す(ユーザーと決めた)。
- 項目は、既定で必須にする。`optional` で省けるようにする。
- 真偽値の項目は、いつも値を持ち、`optional` を付けると断る。3つ目の状態が要るなら select を使う。項目ごとに既定値(`default`。省くと `false`)を持ち、値の無いページは既定値として読む(ユーザーが決めた)。
  - 個人サイトのページの真偽値は、ページごとのスイッチ(連絡先を出す、目次を出す、検索エンジンに載せない など)。「何もしない」側が普段の状態で、特別に扱うページでだけ押す。
  - 後から足すとき、本当にしたいのは「今あるページは今までどおり」で、「未入力」ではない。今までどおりが on のこともある(連絡先をずっと出していて、一部だけ隠したい)ので、既定値を項目ごとに書けるようにする。
  - 「未入力」が要るのは「未設定ならサイト全体の既定に従う」上書きのときだけで、そのときは「既定に従う・出す・出さない」の select の方が、管理画面でも公開サイトでも3つ目の意味が読める。
  - 既定値は、中身の検査(`toContentSchema`)が、値の無いキーに入れる(zod の `.default()`)。server は保存のときに既定値を書き、公開サイトの client は、値の無いページを読むときに既定値を入れて返す。既定値を変えると、値をまだ書いていないページの読み方も変わる。
- 項目は、キーを持つ定義の配列にする。PostgreSQL の jsonb はオブジェクトのキーの順を保たない(短いキーから並べ直す)ので、オブジェクトで持つと、フォームに並べる順が失われる。
- 項目のキーは英字で始まる英数字。中身のオブジェクトのキーになり、公開サイトでは TypeScript のプロパティになる。種類の名前は kebab-case。
- `constructor`・`toString` のような、JS のオブジェクトが元から持つ名前(`Object.prototype` にある名前)は、項目のキーにできない。zod は、中身に無いキーを読むと、継承した関数を値として検査するので、任意の項目にしても省けなくなる(Codex のレビューで見つかった)。
- 項目の入れ子は3段まで、1段に並べる項目は100まで、一度に送る種類は100まで。細工した定義で、検査や再帰を重くさせない。
  - 入れ子の段は、種類の直下の項目を1段と数え、グループと繰り返しごとに1段足す。3段は、グループの中に繰り返しを置き、その中に項目を並べるところまで。
  - 3段に絞るのは、管理画面の横幅のため。管理画面のフォームは、グループと繰り返しの1つごとに枠と左右16pxの余白を付け、繰り返しは要素ごとにも枠を付ける。5段まで許すと、入力欄の幅が最大で約270px減り、スマホでは入力欄がほぼ潰れる(ユーザーが決めた)。
- 値の検査は contract の `content-values.ts` にまとめる。
  - テキストは1〜1000文字で、改行と制御文字を使えない。長いテキストは1〜100,000文字で、改行とタブを除く制御文字を使えない。どちらも、対になっていないサロゲートを断る。PostgreSQL の jsonb は `\u0000` と対になっていないサロゲートを保存できず、そのままでは入力の誤りが 500 になる。
  - URL は、http か https の絶対 URL。zod の `z.url()` は WHATWG の URL の読み方で、改行やタブを取り除いてから受け付ける(テストで分かった)ので、先に改行と制御文字を断る。
  - 日付は `YYYY-MM-DD`。数値は有限の数。
- 定義から中身のスキーマを作る関数(`toContentSchema`)は contract に置く。server(保存のときの検査)と client が、同じ規則を使う。
- 再帰する項目の定義(グループと繰り返し)は、zod の推論が循環するので、`FieldDefinition` の型を書き、スキーマをその型で注釈する。スキーマが型と食い違えば、型検査で落ちる。

## 定義を受け取る(`push/`)

- 送られた種類のうち、まだ無いものは作り、あるものは、ラベルか項目が変わったときだけ書き換える。項目の比較は PostgreSQL の jsonb の `<>` で行い、キーの順によらない。同じ定義を何度送っても何も変わらず、`updatedAt` も進まない。
  - 書き換えは、送られた定義を `jsonb_to_recordset` で表にして、1文の UPDATE で行う。種類ごとに UPDATE を流さない。
  - まだ無い種類は、名前の順に INSERT する。2つのデプロイが、同じ新しい種類を逆の順で送ると、一意の制約の確定を互いに待ち、デッドロックになるため(Codex のレビューで見つかった)。
- 送られなかった種類は消さずに残す。古いサイトに戻したときに、使っているページがある種類を失わないため。種類を消す手段は、フェーズ1では作らない。
- 1つのトランザクションで書き、全部を受け付けるか、何も変えないかのどちらかにする。
- 受け取った種類の名前と、それぞれをどう変えたか(作った・書き換えた・変わらない)と、送ったトークンの ID を、ログに書く。

## 破壊的変更

- 送られた定義を受け付けるのは、その種類のすべての固定ページの中身が、新しい定義の検査を通るときだけ。1つでも通らなければ、`INCOMPATIBLE_PAGES` に、合わないページ(種類・ID・slug・タイトル・合わない場所)の一覧を添えて断り、何も変えない(ユーザーと決めた)。client の CLI は、一覧を出して、0 でない終了コードで終わる。
- 定義どうしの差分ではなく、データで判定する。差分で判定すると、データが入っていなくても型の変更を断ることになり、断る理由を、型の組み合わせごとに決めて持つことになる。データで判定すれば、断るのは「データの入っている項目を壊す」場合に絞られる。
  - データの入っていない項目なら、型を変えても受け付ける。
  - 真偽値の項目は、足しても断らない。値の無いページは、項目の既定値として読むため。
  - 必須の項目を足すと、その種類のページがあれば断る。ページのある種類に必須の項目を足すときは、デプロイを2回に分ける。1回目のデプロイで `optional` の項目として足し、管理画面で各ページにデータを入れてから、2回目のデプロイで必須にする。
  - 使われている選択肢を消すと断る。
- 項目を消すことは、破壊的変更にしない。検査は定義に無いキーを残すので、データは JSONB に残り、フォームに出なくなるだけ(公開 API は、保存した中身をそのまま返す。fixed-pages の `DECISIONS.md`)。古いサイトに戻すと項目の定義が戻り、データもそのまま使える(ユーザーと決めた)。
- 検査の前に、送られた種類のうち、すでにある行のロック(`FOR NO KEY UPDATE`)を、名前の順に取る。保存のときの共有ロックと食い違わず(fixed-pages の `DECISIONS.md`)、同時に2つのデプロイが送っても、ロックを取る順が食い違わない。

## 割り切ったこと

- **真偽値の項目に `optional` を持つ、前の形の定義**:真偽値の項目を既定値の形にする前(フェーズ2の途中まで)に送った定義が DB に残っていると、その種類の定義を読めず、管理用 API の種類の取得と、その種類の固定ページの作成・書き換えが 500 になる。`analemma push-kinds` で定義を送り直せば上書きされて直り、今あるページも新しい定義で通る(値の無い真偽値は既定値になる)。本番の DB はまだ無く、当たるのは手元の DB だけなので、DB の定義を移す仕組み(移る間のためだけのコード)は作らない。

- **深い入れ子の定義**:入れ子の段の上限は、zod が定義全体を再帰して検査した後で確かめる。数百 KB の、深く入れ子にした定義を送ると、上限を確かめる前に zod の再帰が `RangeError` を投げ、500 とログになる。有効なデプロイ用のトークンを持つ人が、細工した定義を送ったときだけ起きるので、受け入れる。
- **3つのデプロイが重なったときのデッドロック**:まだ無い種類を、ロックを取らないまま作る(作れなければ書き換える)ので、同じ種類を含む3つのデプロイが、ミリ秒の差で重なると、ロックの順が食い違い、PostgreSQL がデッドロックとして1つを止め、そのデプロイは 500 で止まる(Codex のレビューで挙がった)。止められたトランザクションは丸ごと取り消され、デプロイを流し直せば済むので受け入れる。
- **断ったときの一覧に出る、公開していないページ**:`INCOMPATIBLE_PAGES` の一覧には、公開していないページの slug とタイトルも含める(自動のセキュリティのレビューで挙がった)。合わないページを一覧で返すことはユーザーが決めたことで、デプロイを止めた人が、どのページを直せばよいかを知るのに要る。トークンを持つのはサイトの持ち主のデプロイの仕組みで、返すのは slug・タイトル・合わない場所(キーと添え字)・zod の issue の messageだけで、中身の値は含まない(zod の issue の message は、期待した型や値だけを書く)。トークンが漏れても、内部用のポートに届く必要があるので受け入れる。
- **同じ新しい種類を同時に送ったとき**:まだ無い種類は、ロックを取れないまま検査に進む。2つのデプロイが同じ新しい種類を同時に送ると、後の方は、先の方が作った種類を、その間に作られたページを検査せずに書き換えうる。デプロイを2つ同時に流し、しかもその間に管理者がその種類のページを作ったときだけ起き、次のデプロイで定義を送り直せば検査されるので受け入れる。
