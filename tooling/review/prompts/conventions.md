## 見る範囲

リポジトリの約束(`AGENTS.md`・`DECISIONS.md`。変更したファイルに近いフォルダのものも含む)のうち、lint とテスト(`bun run check`)とコミットのときの hook では止められないものだけ。

- 設計の原則:DB の形と API の形を分け、mapper でつないでいるか。同じ形を別の場所に手で写していないか。依存の向き(contract はどのワークスペースも import しない、client は contract にだけ依存する)を、lint の届かない書き方で破っていないか。
- 決めたことの置き場所:設計の判断と理由を、関係するコードに一番近いフォルダの `DECISIONS.md` に書いたか。割り切ったことを、末尾の「## 割り切ったこと」に書いたか。約束を変えたなら、`AGENTS.md` も直したか。
- 仕様の置き場所:仕様と振る舞いを、コメントや TSDoc でなくテストで表しているか。
- 抜け道:lint や型検査を通すためだけの不自然なコード(意味の無い分割、型を緩める書き換え、lint の届かない書き方での回避)が無いか。`oxlint-disable` があれば、コードを直せば要らなくならないか、理由が今も成り立つか。lint の設定を緩めたなら、理由を `DECISIONS.md` に書いたか。
- 割り切り:実害の無い失敗のために、手間や約束を足していないか。
- まだ決めていないこと:直下の `AGENTS.md` の「まだ決めていないこと」を、変更が勝手に決めていないか。
- 使わないもの:直下の `AGENTS.md` の「使わないもの」を入れていないか。zod を 4 の書き方で書いているか。
- ほかのリポジトリ:ほかのリポジトリの名前や中身、名前を伏せた言い方(「別のプロジェクトでは」など)を、文書・コード・コミットのメッセージに書いていないか。
- フォルダとファイル:フォルダの名前が中身を言い当てているか(`misc`・`others` のような、何でも入る名前でないか)。200行を超えるファイルを、分割の見出しで見通しよく区切ったか。400行に近いファイルは、分けるべきでないか。
- 触ったフォルダの `AGENTS.md` の、セルフレビューで確かめること(下の「見ない範囲」に入るものを除く)。
- コミットのメッセージの type と scope が、変更の中身に合っているか(形は hook が確かめる)。

## 見ない範囲

- lint・型検査・テスト・hook が止めるもの。整形、lint のルール(コメントの形、TSDoc の形、行数の上限、分割の見出しの形と、200行以下での禁止・400行を超えるファイルでの必須、抑制の書き方、import の境界)、フォルダの件数、名前の kebab-case、テストの置き場所、用語集の「機械で探す語」、コミットのメッセージの形。これらは、`bun run check` と CI が通っていれば守られている。
- 文書・コメント・テストの名前・管理画面の文言の言葉づかいと、用語集に従っているか(言葉の観点)。
- 振る舞いが仕様どおりか、テストが仕様を確かめているか(ビジネスロジックの観点)。
- 認証・認可・入口の守り・入力の境界(セキュリティの観点)。
- 管理画面の操作とアクセシビリティ(UI/UX とアクセシビリティの観点)。
