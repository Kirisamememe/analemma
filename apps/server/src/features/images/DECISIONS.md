# 決めたことと理由(images の feature)

画像を扱う。画像は写真作品を兼ね、別のものにしない(ユーザーと決めた)。

## 列

- タイトル・説明・alt は、どれも任意にする(ユーザーと決めた)。無いときは null にする。
- EXIF から読むのは、撮影日時・カメラ・レンズ・焦点距離・絞り・シャッター速度・ISO だけにする。どれも、無ければ null にする。GPS は読まず、どこにも持たない(ユーザーと決めた)。列はこの表に持つ。EXIF から撮影の情報を読むのは `processing/read-shot-info.ts` で、行に値を入れるのは、画像を作る経路(アップロード・Dropbox からの取り込み)の側。
- 撮影日時は、時差を含まない現地の日時(`timestamp`)と、UTC からの時差(分の整数。分かるときだけ)を、別の列に持つ。EXIF の撮影日時(DateTimeOriginal)は時差を持たず、時差(OffsetTimeOriginal)はカメラによって無い。時差の分からない日時を、UTC などと見なして `timestamptz` に入れると、撮った時刻と違う時刻になる。現地の日時をそのまま出せば、時差が分からなくても、撮った場所の時刻を出せる。
  - API では、現地の日時を時差を含まない ISO 8601 の形(`2025-05-01T14:03:27`)で、時差を `+09:00` の形で返す。
  - 時差だけがあって日時の無い行と、±18時間を超える時差は、DB の check の制約で断る。実在する時差は −12:00〜+14:00 なので、余裕を持たせて区切り、読み取りの誤りで、ありえない値が入らないようにする。
- カメラとレンズは、それぞれ1つの文字列で持つ。メーカーと機種を分けて引く使い方が無く、出すときも1つの文字列にするため。
- 焦点距離(mm)・絞り(F 値)・シャッター速度(秒)は数で持つ。EXIF では分数で持つが、`1/250` のような出し方は使う側が決める。
- シリーズとは多対多で、並び順はシリーズごとに持つ(ユーザーと決めた)。シリーズの側の表で持つので、この表に列を足さない。
- CMS は原本を持たない(ユーザーと決めた)。配信用の画像は、この表に列を足さず、別の表に持つ(「配信用の画像」)。

## 写真の登録

- 写真1枚から撮影の情報を読み、配信用の画像をすべて変換してから DB のトランザクションを始める。変換を待つ間は接続を占有しない。対応しない形式には画像の ID を割り当てない。
- 配信用のファイルの名前に、画像の ID とは別の UUID を使う。幅ごとのファイルを書き終えてから、DB のトランザクションで画像と配信用の画像の行をまとめて作る。配信は DB の行で引くため、書き終えていない画像は取得できない。書き込みが失敗したら、書きかけのファイルも含めて消す。
- トランザクションの確定に失敗したときは、PostgreSQL の `pg_xact_status` でロールバックを確認してからファイルを消す。行が見つからないだけではロールバックと判定できない。確定の応答が届く前に接続が切れ、別の接続で読み直した後に登録が確定する場合がある。

## 直接アップロード

- 管理画面は、写真を1回の送信に1枚ずつ送る(`admin.images.upload`)。oRPC の procedure にして、ほかの管理用 API と同じ base で、認可と Origin の確認を掛ける。1枚ずつなら、写真ごとに結果を返せて、失敗した写真だけを送り直せる。変換は1枚ずつしか流さないので、まとめて送っても速くならない。
- 写真のファイルは 64 MiB まで(contract の `PHOTO_MAX_BYTES`。管理画面は送る前に確かめる)。今のカメラとスマートフォンが書く JPEG・HEIC は、1億画素の機種でも収まる。超えるのは 16-bit の PNG のような書き出しで、配信用には長辺 2560px に縮めるので、JPEG で書き出し直して送れば足りる。上限の値は、ユーザーとまだ決めていない(`apps/server/AGENTS.md` の「まだ決めていないこと」)。
- 本文の上限は、写真の上限に、ほかの API の上限(1 MB)を足した値にする。この上限は、`/api/admin/images/upload` へのリクエストで、セッションが続いているときだけ掛け、ほかは 1 MB のままにする(`app.ts`)。oRPC は認可の middleware より先に本文を読むので、誰にでも大きな上限を掛けると、ログインしていない人に、1回で 65 MB をメモリに読ませられる。Hono と oRPC でパスの読み方が食い違っても、大きな上限が掛かるのはログイン中の管理者のリクエストだけで、写真に 1 MB が掛かれば 413 になるだけ。
- 形式は、ファイルの種類(MIME)ではなく中身で見分ける。HEIC を知らないブラウザは、種類を空で送る。
- 写真の変換は、プロセスの中で1つずつ流す(`processing/conversion-queue.ts`。context の `conversions`)。1枚の変換でメモリが 0.3〜0.6 GB に達するため。画像を作る経路は、どれも `createImage` を通り、同じキューに並ぶ。待つ間は、受けた写真の bytes をメモリに持つ。
- 同時に受ける写真は2枚まで(変換している1枚と、次に変換する1枚)にし、3枚目は本文を読まずに 503(`Retry-After`)で断る(`app.ts`)。数えるのは、本文を受け始めてから応答を返すまで。数えないと、ログイン中のリクエストが重なるたびに、待つ写真の bytes がメモリに積み上がる。管理画面は1枚ずつ送るので、2つのタブから送っても断られない。
- ログイン中に写真を送るリクエストだけ、120秒まで何も送り受けしなくても接続を切らない(`main.ts` が Bun の `server.timeout` を呼ぶ関数を、`createExternalApp` に渡す)。変換を待つ間は応答を返せず、Bun の既定の10秒では切れるため。ほかのリクエストとログインしていないリクエストは、既定の10秒のまま。NAS で変換の時間を測って見直す。

## 配信用の画像

- 配信用の画像(AVIF)は、画像1枚につき、幅の段ごとに1行を `delivery_image` に持つ。列は幅・高さ(px)と、置き場所の中のファイルの名前。主キーは画像の ID と幅で、同じ幅の段は1つだけにする。段の数と幅は、変換の側が決める(`processing/DECISIONS.md`)。
- 画像を消すと、配信用の画像の行も FK の cascade で消える。
- 配る URL と、置き場所の中のファイルの名前を分け、ファイルの名前を列に持つ。配る経路は、URL の画像の ID と幅で行を引き、行にあるファイルの名前で読むので、URL がそのままファイルのパスにならない。
- 管理用 API は、配信用の画像を、幅・高さ・URL の一覧で、幅の昇順に返す。配信用の画像をまだ作っていない画像は、空の一覧にする。URL は、管理画面と同じ origin の、`/` で始まる path(`/media/<画像の ID>/<幅>.avif`)にする。管理画面の CSP の `img-src 'self'` のまま使える。公開サイトが使う URL は、公開 API を作るときに決める。
- 一覧と取得だけでなく、書き換え・公開・非公開の出力にも、同じ形で入れる。管理画面は、書き込みの結果で取得の結果を置き換えるため。
- 書き換え・公開・非公開の procedure は、画像の行を書く前に、配信用の画像を読む。書いた後に読むと、読み取りが失敗したときに、書き込みが確定したまま 500 を返し、管理画面は変える前の状態を持ち続ける。

## 配信

- 配信用の画像は、外部用のポートの `GET /media/<画像の ID>/<幅>.avif` で返す(`delivery/serve-delivery-image.ts`)。ブラウザの `<img>` がそのまま読める AVIF の本文を返すので、oRPC の procedure にせず、`app.ts` が Hono の route から呼ぶ。
- path は、percent-encoding を解かずに、決まった形(小文字の UUID と、0 で始まらない幅)とだけ照らし合わせる。照らし合わせた画像の ID と幅で行を引き、行にあるファイルの名前で読む。
- 公開の画像は、誰にでも返す。非公開の画像は、管理画面で見せるため、管理者のセッションがあるときだけ返す。
- 無い画像・無い幅・形の違う path・非公開でセッションの無いリクエストは、どれも同じ 404(本文は空)にする。非公開の画像があることを、応答の違いで知らせない。
- 非公開の画像でセッションを見るのは、`Sec-Fetch-Site` が `same-origin` か `none`(利用者がアドレスバーなどから開いた)ときだけ。セッションの Cookie は `SameSite=Strict` でも、同じサイトの別の origin のページ(公開サイトなど)からのリクエストには付く。そうしたページに、管理者のブラウザで非公開の画像を読み込ませ、幅や高さを読ませない。
- セッションは確かめるだけで、期限を延ばさず、Cookie も書かない。`<img>` の読み込みは、管理画面がログインの最中に止められない。期限を延ばした応答とログインし直した応答が逆の順で届くと、新しい Cookie が古い token で上書きされうる(`src/features/auth/DECISIONS.md` の「割り切ったこと」の「応答が逆の順で届くとき」)。期限は、管理用 API を呼んだときに延びる。
- `Cache-Control` は、公開の画像を `public, max-age=3600, must-revalidate`、非公開の画像を `private, no-store`、404 を `no-store` にする。非公開の画像を、共有のキャッシュにもブラウザにも残さない。404 は、HTTP の既定ではキャッシュに残りうるので、公開した後やログインした後に取れるよう、残させない。公開の画像に `must-revalidate` を付けるのは、1時間を過ぎた応答を、配信元が落ちているときなどに確かめずに返させないため。
- 行があるのに置き場所にファイルが無いときは、404 を返し、logger に error で書く。

## 公開状態

- 既定は公開で、作った時点で公開になる(ユーザーと決めた)。新しいページを公開していない状態で作る固定ページとは違う。
- 公開状態は、固定ページと同じく `publishedAt` の有無で持つ。公開状態の判定は、`queries/images.query.ts` の `isPublished` だけで行う。
- 公開し直しても、非公開にする前の `publishedAt` には戻さず、公開し直した日時にする。公開しているまま公開し直しても、`publishedAt` は変えない(固定ページと同じ)。
- 非公開の画像を、公開 API で取れなくすることは、公開 API のタスクで作る。配信では、管理者のほかには返さない(「配信」)。
- 固定ページやシリーズが使っている画像でも、非公開にも削除にもできる。使っていることを理由に止めない(ユーザーが決めた)。公開サイトは、画像を取れなければ、取れないときの表示に切り替える。整合を保つために、使う人に手順を強いない。

## 書き換え

- 管理用 API で書き換えるのは、タイトル・説明・alt。3つを丸ごと送らせて置き換え、空にするときは null を送らせる(空の文字列は断る)。
- `updatedAt` は、タイトル・説明・alt を変えたときだけ進める。同じ値のまま保存し直したときと、公開と非公開の切り替えでは進めない(固定ページと同じ)。

## 一覧

- 管理用 API の一覧は、公開しているかによらず、新しく足した順(ID の降順)に並べる。ID は `uuidv7()` で作るので、作った時刻の順に並ぶ。撮影日時の順のような、ほかの並べ方は、管理画面の画面を作るときに決める。
- ページ送りは、ページの最後の画像の ID を cursor にして、その ID より小さいものを読む。件数で飛ばす方式(offset)では、取り込みの途中で画像が足されると、ページの境目がずれ、同じ画像が重ねて出る。ID で比べれば、cursor の画像が消されても、続きを読める。
- 1ページは、既定で50件、多くて100件にする。
- 管理画面の、1枚の写真を見る画面の前後のボタンのために、一覧の並びで一つ新しい画像と一つ古い画像の ID を返す procedure を置く(`neighbors`)。一覧の cursor は古い方へしか読めないので、新しい方の画像を引けない。読み込んだ一覧から引くと、URL を直に開いたときや、読み込んだ範囲の端で引けない。
- 対象の画像とその前後は1回の SQL で読む。削除が重なっても同じ時点の並びになり、主キーの index からそれぞれの隣を1件ずつ取れる。
- 一覧と取得は、撮影の情報を含む同じ形を返す。1件の列が少なく、一覧で除いても軽くならないため。

## 削除

- 画像の削除は、物理削除にする(ユーザーが決めた)。消した画像は、管理用 API から無くなる。非公開にすれば残したまま見せずにおけるので、戻せる削除は持たない。
- 画像を消すと、その画像の `series_image` の行も FK の cascade で消える。非公開にしてもシリーズとの関係と並び順は残る。
- 配信用の画像は、行を FK の cascade で消し、ファイルを置き場所から消す。消すファイルの名前は、画像の行を消す前に読んでおき、行を消した後でファイルを消す。先にファイルを消すと、行を消せなかったときに、ファイルの無い行が残る。行を消した後なら、ファイルを消せなくても、配る経路からは届かない。

## テスト

- 写真から画像を作ることは、直接アップロードの API 越しのテスト(`creating/__tests__/upload-image.test.ts`)で確かめる。登録の途中で失敗したときの後始末は、DB とファイルの書き込みを差し替えるので、`createImage` を直接呼んで確かめる。
- 一覧・取得・書き換え・公開・削除のテストは、画像の行をテストの中で DB に直接入れる。写真を変換すると1枚ごとに秒単位で待ち、並びや日時を決めた行を何枚も作るテストが遅くなるため。

## 割り切ったこと

- **登録の確定が分からないときのファイル**。DB に届かないか、確定を一度調べた時点でトランザクションの結果がまだ分からないときは、ファイルを残す。すでに登録した写真の配信用の画像を失わないため。プロセスがファイルを書いた後で終了した場合も、行の無いファイルが残りうる。行が無ければ配信されず、置き場所で照合できるので、復旧後に自動で照合する処理は作らない。

- **消せなかったファイル**:画像の行を消した後に、ディスクの失敗などでファイルを消せないと、想定外の失敗(500 とログ)になり、ファイルが置き場所に残る。画像はもう消えているので、管理者がやり直すと `NOT_FOUND` になる。残ったファイルを指す行は無く、配る経路からは届かないので、データは漏れない。消せないのはディスクが壊れたときくらいで、残ったファイルは置き場所を見れば消せるので、やり直しの仕組みは作らない。
- **応答を受け取れなかった写真の送り直し**:写真を登録した後で応答が届かず(通信が切れるなど)、管理者が同じ写真を送り直すと、同じ写真の画像が2つできて、どちらも公開される。2つとも一覧の先頭に並ぶので、片方を消せば済む。防ぐには、送り直しを見分ける ID を管理画面が作って送り、画像の行に一意に持たせる仕組みが要る。個人の CMS で、通信が切れるのはまれなので作らない。
- **キャッシュに残る公開の画像**:公開の画像は、ブラウザと途中のキャッシュに1時間まで残させるので、非公開にしたり消したりしても、すでに読んだブラウザや途中のキャッシュからは、最長1時間見える。毎回確かめさせる(`no-cache` と、`ETag` か `Last-Modified` での条件付きのリクエスト)には、ファイルが変わったことを示す値を持ち、条件付きのリクエストを受ける仕組みが要る。個人のサイトで、1時間の遅れは困らないので、公開サイトのキャッシュの設計と一緒に見直す。
