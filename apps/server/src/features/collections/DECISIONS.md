# 決めたことと理由(collections の feature)

- コレクションと画像は多対多で、`collection_image` にコレクションごとの位置を持つ。コレクションと画像の ID を合わせた主キーで、同じコレクションに同じ画像が重なるのを防ぐ。
- 公開状態は `publishedAt` の有無で持ち、コレクションは物理削除する。コレクションと画像のどちらを消しても、関係する行は FK の cascade で消える。片方を非公開にしても、もう片方の公開状態と画像の並びを保つ。
- 名前・slug・説明の書き換えでは、ほかのコレクションに使われていない slug かを確かめてから書き、使われていれば `SLUG_TAKEN` で断る。作成の重なりは `ON CONFLICT DO NOTHING` で `SLUG_TAKEN` にする。
- 画像の出し入れと並べ直しでは、先にコレクションの行のロックを取る。空のコレクションへの追加が重なっても、末尾が決まってから次の追加が始まる。追加では、渡された画像がすべてあることを確かめ、終わるまで画像の削除を待たせる。無い画像があれば `NOT_FOUND` で断る。
- 並べ直しでは、関係する行のロックを取ってから ID を照らし合わせる。画像の不足・余分・重複は `ORDER_MISMATCH` で断り、そろっていれば1文の UPDATE で位置を振り直す。
- 管理用の一覧と取得は、非公開の画像も配信用の URL と一緒に返す。画像の公開状態は、コレクションから外すことなく管理画面で確認できる。

## 公開 API

- slug でコレクションを引き、非公開なら無いコレクションと同じく `NOT_FOUND` を返す。コレクションの公開状態の判定は `published/queries/published-collections.query.ts` の `isPublished`(行を見る)と `matchPublished`(SQL の条件)で行う。
- 一覧は管理用 API と同じく新しく作った順に返す。一覧のカバーと件数は同じ SQL で読み、並べ直しや非公開への切り替えが重なっても同じ時点の並びを使う。

## 割り切ったこと

- **書き換えの slug の競合**:同時に2つのコレクションを同じ slug に書き換えると、後の方が一意の制約で失敗し、500 とログになる(固定ページと同じ)。管理者は1人で、ミリ秒の差で同じ slug を2つのコレクションに付けることはまず無い。防ぐためにコレクションの表全体をロックすると、説明だけの保存でも、ほかのコレクションの作成や公開を待たせる。
