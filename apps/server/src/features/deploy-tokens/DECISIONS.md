# 決めたことと理由(deploy-tokens の feature)

デプロイ用 API(`deploy`)を呼ぶための、デプロイ用のトークンを扱う。

## トークンを求める理由

- デプロイ用 API は、内部用のポートに置いたうえで、トークンも求める(ユーザーと決めた)。内部用のポートは、同じマシンのほかのアプリやコンテナからも届くので、それらを信頼しない。
- 公開 API にはトークンを求めない。返すのは公開しているコンテンツだけで、内部用のポートの外には出さないため(`apps/server/DECISIONS.md` の「2つのポート」)。

## トークンの形と持ち方

- トークンは、管理者が管理用 API で発行する。token を返すのは発行したときの1回だけで、一覧にも出さない。
- 形は、セッションの Cookie と同じ `{id}.{secret}`。DB には ID と secret の SHA-256 だけを置き、secret のハッシュは定数時間で比べる。作り方と比べ方は、auth の feature の `secret-token/` を使う(理由は `src/features/auth/DECISIONS.md` の「token」)。
- 呼ぶ側は、`Authorization: Bearer {token}` で送る。断るときは、401 と `UNAUTHORIZED` に、`WWW-Authenticate: Bearer` を添える。
- できることは、種類の定義を送ることだけにする(ユーザーと決めた)。デプロイ用 API のアクセス区分には、ほかの procedure を置かない。
- 期限は持たない。取り消すまで使える。デプロイの仕組み(CI の secret など)に置くトークンなので、期限で切れると、ある日突然デプロイが止まる。漏れたときは、管理画面で取り消す。
- 発行と取り消しに、再認証は求めない。トークンでできるのは定義を送ることだけで、ページを消したり、データの入った項目を壊したりはできない(壊れる変更は断る)。漏れた Cookie で発行されても、管理者は一覧で見つけて取り消せる。
- 一覧には、名前・発行した日時・最後に使った日時だけを出す。最後に使った日時は、トークンを確かめるたびに書く。送るのはデプロイのときだけなので、書く回数は少ない。
- 確かめられなかったときは、token の ID(読めたときだけ)をログに書き、secret は書かない。

## 割り切ったこと

- **最後に使った日時と、断った定義**:最後に使った日時は、定義を受け付けたかどうかに関わらず、トークンを確かめた時点で書く。断った定義を送ったときも進むが、トークンが使われたことには変わりないので受け入れる。
