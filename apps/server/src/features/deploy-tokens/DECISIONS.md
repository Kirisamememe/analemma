# 決めたことと理由(deploy-tokens の feature)

デプロイ用 API(`deploy`)を呼ぶための、デプロイ用のトークンを扱う。

## トークンを求める理由

- デプロイ用 API は、内部用のポートに置いたうえで、トークンも求める(ユーザーと決めた)。内部用のポートには、同じマシンのほかのアプリやコンテナからも届くので、それらを信頼しない。
- 公開 API にはトークンを求めない。返すのは公開しているコンテンツだけで、公開 API は、サーバーの外から届かないため(`apps/server/DECISIONS.md` の「2つのポート」)。

## トークンの形と持ち方

- トークンは、管理者が管理用 API で発行する。token を返すのは発行したときの1回だけで、一覧にも出さない。
- 形は、セッションの Cookie と同じ `{id}.{secret}`。DB には ID と secret の SHA-256 だけを置き、secret のハッシュは定数時間で比べる。作り方と比べ方は、auth の feature の `secret-token/` を使う(理由は `src/features/auth/DECISIONS.md` の「token」)。
- 呼ぶ側は、`Authorization: Bearer {token}` で送る。断るときは、401 と `UNAUTHORIZED` に、`WWW-Authenticate: Bearer` を添える。
- できることは、種類の定義を送ることだけにする(ユーザーと決めた)。デプロイ用 API のアクセス区分には、ほかの procedure を置かない。
- 期限は持たない。取り消すまで使える。デプロイの仕組み(CI の secret など)に置くトークンなので、期限で切れると、ある日突然デプロイが止まる。漏れたときは、管理画面で取り消す。
- 発行の前に、今のパスキーで確かめ直させる(再認証。自動のセキュリティのレビューで見つかった)。漏れたセッションの Cookie を持つ人がトークンを発行すると、ログアウトの後も、期限の無い、定義を送る手段が残る。トークンではページを消せず、データの入った項目も壊せない(破壊的変更は断る)が、定義を書き換えて、管理画面のフォームから項目を消したり、保存のときの検査を変えたりして、管理者の編集を妨げられる。パスキーの追加に再認証を求めるのと同じ理由(`src/features/auth/DECISIONS.md` の「再認証」)。
  - 再認証の options は `admin.session.reauthenticationOptions` で取り、発行のリクエストに資格情報(`assertion`)を添えさせる。発行と同じトランザクションで、セッションがまだあることを確かめ、再認証に使ったパスキーの使用を書く。
- 取り消しには、再認証を求めない。取り消しは手段を減らすだけで、漏れた Cookie で取り消されても、デプロイが止まるだけで、管理者が発行し直せば済む。
- 一覧には、名前・発行した日時・最後に使った日時だけを出す。最後に使った日時は、トークンを確かめるたびに書く(定義を断ったときも進む)。送るのはデプロイのときだけなので、書く回数は少ない。同時のリクエストで古い時刻が後から書かれても戻らないよう、今の値より新しいときだけ進める。
- 行を読んでから利用を記録するまでの間に取り消されたら、記録が0行になるので断る(Codex のレビューで見つかった)。
- 確かめられなかったときは、token の ID(読めたときだけ)をログに書き、secret は書かない。

## 割り切ったこと

- **取り消しと重なったときのテスト**:行を読んでから利用を記録するまでの間に取り消されたら断ることは、テストで確かめていない。2つのリクエストを、その間に決まった順で重ねる仕組みが要る。壊れると、取り消しとミリ秒の差で重なったリクエストが1回だけ通る(下の「記録した後の取り消し」と同じ結果)ので、確かめる仕組みを作るほどではない。
- **記録した後の取り消し**:利用を記録した後に取り消されると、そのリクエストは定義を受け取るところまで進む。取り消しの確定と、すでに確かめたリクエストが、ミリ秒の差で重なったときだけ起き、そのトークンで送れるのはその1回だけなので受け入れる。
